# Terminal Twin, Agent Guide

## Overview

**Terminal Twin** is an event-driven digital twin of a large automated container terminal (reference: TTI Algeciras), built as a TOS test bench. Spec: GitHub issue #24. Vocabulary: [`GLOSSARY.md`](../../../GLOSSARY.md) at the repo root, use its terms in code, tests and docs. Background on the real terminal and the sim's deliberate deviations: [knowledge-base/dk_ops__tti_algeciras_operations.md](../../../knowledge-base/dk_ops__tti_algeciras_operations.md). Reference photos: `docs/reference/` at the repo root.

The headless engine covers vessels and berthing, STS cranes and hatch covers, SHC transport, paired ASC block storage, export load, transshipment and empties, rehandles, landside trucks, the yard start modes, KPIs and end conditions, and the TOS decision points. The browser host runs the engine in a Web Worker and adds a 3D scene (Blender-generated GLB assets), debugger, dashboard, saves and rewind, and locale and units.

**Sim ID:** `terminal-twin`. **Engine version:** `engine/simulation.ts#ENGINE_VERSION`.

**Entry routes.** `/sim/terminal-twin` boots one of two apps from `TerminalTwin.vue`; a URL-level change (a new switch, a boot-time default) covers both:

| Route | App | Dev API | Render loop | URL switches |
|---|---|---|---|---|
| `/sim/terminal-twin` | the twin | `window.__tt` (`dev/devApi.ts`) | `composables/useTwinScene.ts` | `?quality=`, `?render=off` via `modules/urlSwitches.ts`; `__tt.renderOnce()` |
| `/sim/terminal-twin?viewer=<asset>\|yard` (dev server and smoke build only) | asset viewer `dev/AssetViewer.vue` | `window.__ttAssets` (`dev/assetViewerApi.ts`) | `dev/assetViewerScene.ts` | the same parser through `dev/viewerRender.ts` (#345): `?render=off` keeps auto LOD and orbit updates and skips the draw (`__ttAssets.frames()` advances at 0 calls); a fixed `?quality=low\|medium` takes that level's shadows and resolution; `__ttAssets.renderOnce()` draws one frame and returns its calls and triangles |

## Test levels

Put each check at the lowest level that can see the behaviour; a smoke spec is the slowest and costs CI minutes on every PR that selects its group.

| Level | Where | What belongs there |
|---|---|---|
| Engine unit tests | `tests/*.test.ts` (Vitest, Node) | events, state, invariants, strategies, KPIs, goldens: anything `sim.query` can read |
| Headless scene | `headlessScene()` (`cli/headlessScene.ts`), `tests/headless-scene-*.test.ts` | what the 3D scene holds or poses (`sceneState()`, `stats()`) when no DOM, click or pixel is involved |
| Component tests | `tests/components/` (happy-dom) | what a panel, menu or dialog shows and the store change or request a choice causes; a panel that reads engine data mounts with the real store over the engine host in-process (`vi.mock` of `modules/engineClient`, as `bay-viewer.test.ts`), and the saves dialog over a fake save store |
| Smoke specs | `tests/browser/*.smoke.ts` (Playwright) | wiring in the real app: a control opens and a choice reaches the running twin; pixels, draw calls, frame rate; the production build; equipment rig state built from the GLBs (LOD switching, ropes, wheel roll and steering, articulation, hero choice, spreader length), because the headless scene loads no GLBs and their pose maths already has unit tests (`asc-rig`, `shc-pose`, `truck-pose`, `spreader-mode`, `hero-equipment-*`; decided in #337) |

A smoke spec boots the sim only through `openTwin(page, { scenario })` (`tests/browser/openTwin.ts`): smoke build, `?quality=low&render=off`, wait for `window.__tt`, load the scenario. It opts in to `render: true`, a `quality`, a `viewport`, `params` or `devApi: false` (production build) only when that is what it checks, with a one-line reason at the call; the option list and when each applies are in that file's header. Dev specs import `test` from `tests/browser/twinTest.ts`: one page per worker, reset before every test; `test.use({ fresh: true })` with a reason opts out (#329, details in the proof table below). Load the smallest fixture that proves the behaviour (`tracer-1sts-10-boxes` for HUD and DOM checks; a named fixture such as `two-vessels-compete-for-berth` for one behaviour). A TTI preset (baseline or peak day) costs 4 to 7.5 s of load and the heaviest scene, so keep it for scale only: draw and frame budgets, the overview at TTI size, scenery that exists only in TTI, the HUD fit of TTI's KPI strip, or an engine that cannot keep up (#334).

Never regenerate goldens to make a failing test pass unless the behaviour change is intended and explained in the commit. Without `--update` / `UPDATE_GOLDEN=1` nothing ever rewrites a golden. Two branches that both regenerate a golden conflict on merge: regenerate on the merged tree instead of hand-merging, and plan a change that moves every golden (a default flip) as its own ticket (`docs/agents/implementing.md`).

All three commands print usage with `--help`. Exit codes: `tt:run` 0 ok / 1 violation or error / 2 usage; `tt:diff` 0 identical / 1 diverged / 2 usage; `tt:golden` 0 all match / 1 drift or missing / 2 usage.

### Headless scene

- `headlessScene(name, { seed, quality, camera, startDateTime, lockDaylight, ...edits })` (`cli/headlessScene.ts`) loads a fixture or preset like `__tt.load`, drives the engine through the browser's `TwinController` (worker host in-process), builds and poses the scene through the same `SceneDriver` (`modules/sceneDriver.ts`) the render loop uses, and returns `sceneState()` in `__tt.sceneState()`'s shape (built by the shared `sceneStateOf`) plus `stats()` (`__tt.scene()`'s draw-independent counts); `runUntil`, `runTo`, `step`, `setColourBy`, `setOverlays`, `setCameraPose`, `cameraTo`, `setLockDaylight` mirror the dev API, `atmosphere()` returns `__tt.atmosphere().scene`, and `setLive(true)` runs the frame as during playback (gantry beacons and alarms only animate while live).
- No WebGL and no GLBs: hulls read `assets: 'placeholder'`, GLB rig state (`stsRendered`, `shcRigs`...) stays empty.
- Moved here:
  - the vessel group's colour-by tints, ROB boxes and hatch panels;
  - the engine group's ASC, paired ASC, load, rehandle, SHC and truck scene checks: `tests/headless-scene-engine.test.ts`, #333;
  - the equipment group's SHC spawn yaw and gantry beacons: `tests/headless-scene-equipment.test.ts`, #337, whose GLB rig checks stay in the browser;
  - the yard group's container LOD and livery, close-up counts by pose, gate infrastructure instances and lighting per hour with the daylight lock: `tests/headless-scene-yard.test.ts`, #336, with hero caps, rungs and arrival in `hero-faces.test.ts` and `hero-prep.test.ts`.
- The engine group's only browser test is the worker running the ASC import fixture to its golden hash, `terminal-twin-asc.smoke.ts`.
- `headless-parity.smoke.ts` keeps the two in step.

### Browser smoke specs

- Playwright smoke tests in `tests/browser/*.smoke.ts` pass (`dev` project: the smoke build with `window.__tt`, locally and in CI, so hashed asset names such as `hero-shc-<hash>.glb` match the same way in both; `SMOKE_SERVER=dev` opts in to the Vite dev server for hot-reload debugging; `prod` project: a production build).
- Not part of `pnpm test`; CI runs them in the required `smoke` job (`--grep-invert @load`).
- Specs tagged `@load` need a real frame rate and never run in CI: run them locally.
- Write frame-based checks with `tests/browser/frameSampling.ts` (ratios over a minimum wall-clock window, never absolute frame counts).
- Booting the sim: **Test levels** above.
- Asset-viewer specs (`?viewer=<asset>`, no `__tt`) open `page.goto(twinUrl({ params: { viewer } }))` (render off and Low there too, #345: they call `__ttAssets.renderOnce()` before a screenshot; the yard budget spec asks for `quality: 'high'` so its measured frame keeps the shadow pass), and quality-ladder and hero specs set the level they test with `__tt.setQuality` or `setAutoRung` after `openTwin`.
- Dev specs import `test` and `expect` from `tests/browser/twinTest.ts` (#329): each Playwright worker keeps one booted page, and before every test the fixture clears its listeners, routes, viewport and emulated media and calls `window.__appReset()` (`src/utils/smokeReset.ts`, dev and smoke builds only: the sim unmounts, storage is cleared, every Pinia store is disposed); `openTwin` then routes to the twin in-app with no page load.
- A spec that needs a real first load (context options such as locale, time zone or touch; `addInitScript`; reloads that rely on IndexedDB saves or persistence) opts out with `test.use({ fresh: true })` and a one-line reason; `SMOKE_FRESH_PAGES=1` gives every test a fresh page (to rule out a leak or compare timings).
- `shared-page-reset.smoke.ts` checks the reset; the suite passed in shuffled order (`--shuffle 329`).

## Extending (checklist)

Full detail: [docs/architecture.md#extending](docs/architecture.md#extending) and, for strategies, [docs/decision-points.md](docs/decision-points.md).

- Engine imports go through `engine/index.ts` outside `engine/` and `scenario/` (lint enforces it).
- New event type: `EventPayloads` in `engine/events.ts` plus a reactor in a subsystem `ReactorMap` listed in `REACTORS` (`engine/simulation.ts`).
- New invariant: append to `INVARIANTS` with a dotted id, `reads` and (if it reads a lot) `scoped: true`; add a test that triggers it.
- New strategy: register it for its decision point. Note that some strategies (chained, paired, predispatch SHC dispatch, ASC pre-retrieval, grouped decking, ISO empties) are switched on in the engine by the configured strategy name, so a named handler set is not the same as choosing a strategy.
- New fixture: `scenario/fixtures/definitions.ts`, `pnpm run tt:fixtures`, import in `fixtures/index.ts`, `UPDATE_GOLDEN=1 pnpm test`.
- New smoke spec: **Test levels** above, and the smoke spec review rules in `docs/agents/tooling.md`.
- New KPI: `KPI_DEFS` and an `observe` case in `engine/kpi/collector.ts`, `KPI_GROUPS` in `modules/dashboardModel.ts`, a `dashboard.kpi.<id>` catalogue key.
- New equipment kind: one `modules/equipmentKinds/<kind>.ts` added to `EQUIPMENT_KINDS`.
- Any change that moves an event log: bump `ENGINE_VERSION`, update goldens deliberately, and update the docs.
