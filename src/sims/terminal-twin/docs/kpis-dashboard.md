# Terminal Twin: KPIs, final report and dashboard

The KPI collector, end conditions, final report and the dashboard tab. Guide: [terminal-twin-AGENTS.md](../terminal-twin-AGENTS.md). Terms: [GLOSSARY.md](../../../../GLOSSARY.md).

## KPIs, end conditions and final report (TT-07)

- **Collector** (`engine/kpi/collector.ts`, `clock.ts`, `headline.ts`; `engine/export.ts`). `Simulation.kpiSeries()` returns every KPI as hourly, per-shift and whole-run series (`KpiSeriesReport {clock, elapsedS, hours, shifts, series[id].entities[entity] = {hourly[], shifts[], total}}`; null = no data). The collector is a pure fold over the committed events (`commit()` feeds it); a snapshot restore rebuilds it by replaying the log, so it is never stored and does not touch the event-log hash or the goldens. It stores per-hour **components** (counts, seconds in a state, metres, gauges) and each KPI is a function of the summed components of a window, so shift and run values are exact (never averages of averages). Open states (a crane waiting, an ASC mid-cycle) are closed at `now` on a copy when a report is built.
- **Buckets.** Hours are cut on the scenario clock (a 06:30 start gives a half-hour first bucket); shifts are 3 x 8 h of whole hours (default 06-14, 14-22, 22-06; night shift belongs to the day it starts). The clock comes from `config.kpi {startTimeOfDayS?, shiftStartHour?}`; default is `startDateTime` read in UTC (machine independent). The browser's `runConfigFor` sets `startTimeOfDayS` from the local start time so shifts match the clock on screen.
- **KPIs** (`KPI_DEFS`, add rows there plus an `observe` case for new events): quay `sts.moves`, `sts.gross-moves-per-hour` (moves per hour on a vessel, i.e. not waiting for work), `sts.net-moves-per-hour` (also minus waiting for SHC and for the rail), `sts.wait-shc-s`, `sts.wait-work-s`, `sts.wait-rail-s`, `berth.moves-per-hour`, `vessel.remaining-moves` (gauge), `vessel.turnaround-s` (counted in the hour of departure) and `vessel.anchorage-wait-s` (hour of berth allocation); horizontal (only with SHCs) `shc.loaded-pct|empty-pct|idle-pct`, `shc.empty-travel-ratio`, `shc.empty|loaded-distance-m`, `shc.handovers`, `shc.state.<state>-s` (seconds in each of the seven SHC operational states, TT-R11), `shc.jobs`, `shc.cycle-time-s`, `wtp.dwell-s` (per block, drop to ASC pick); yard (only with blocks) `asc.utilisation-pct`, `asc.jobs`, `asc.cycle-time-s`, `yard.fill-pct` (gauge per block, from `AscStacked`; TT-10/13 retrieval must lower it); TOS handlers `handler.calls|mean-latency-s|wall-latency-s|fallbacks|failures|backlog|equipment-idle-s` per decision point (idle = sim latency x waiting equipment, read from the `DecisionResolved` subjects). Handler **wall** latency is in the event log (`DecisionResolved.payload.wallLatencyMs`, absent when 0) and is a series, `handler.wall-latency-s` (mean per bucket, derived from the log so it works after a load or rewind); the run totals stay in `kpiReport().handlers[dp].wallLatencyMs` and the final report's handler table. Cross-checks against the engine counters are in `tests/kpi-collector.test.ts`.
- **Hatch covers (TT-R09):** `kpiReport().hatch` (only once a hatch move has started) holds the totals: hatch `moves` (`removes` + `replaces`), `stsTimeS` (STS time on hatch moves, start of a move to the panel set down), `waitS` (crane idle for a lashing release or a securing) and the same per STS. These are report totals, not a bucketed series (no `KPI_DEFS` row yet). Hatch moves are not in `sts.moves` or the moves-per-hour rates; the crane's `lastMoveEndS` includes them, so hatch time lowers gross moves per hour and lengthens `vessel.turnaround-s`. The CLI prints a `Hatch covers:` block.
- **Headline and highlights** (`headlineKpis`, `highlightsOf`): the strip and CLI numbers; highlights = hardest-working crane, busiest block, busiest SHC and the longest wait (anchorage, SHC or rail). Both are pure functions of the series and `kpiReport()`, so the CLI, worker and UI agree (`tests/kpi-host.test.ts`).
- **End conditions**: `config.endConditions {vesselsCompleted?, simDurationS?, moves?}`; none set means all scheduled vessels; the first one met ends the run (`tests/end-conditions.test.ts`). The setup dialog's "End conditions" fieldset (`modules/endConditions.ts`) only replaces the scenario's own once edited; vessels blank means all scheduled. CLI: `--end moves:<n> | vessels:<n> | time:<s>` (repeatable).
- **Final report** (`components/FinalReport.vue`): a docked panel (not a modal) that appears when the display reaches the end (`store.runEnded`). It shows the reason (`modules/endReason.ts`), highlights (`modules/highlights.ts`), headline KPIs, cranes, vessels and TOS-handler tables (calls, fallbacks, sim and wall latency, equipment idle) and the export buttons; it can be closed and reopened. After the end the clock is frozen: speed buttons, pause, Run to, Step and their shortcuts are disabled (store actions are no-ops); Reset and New Scenario work; the scene, selection, inspector and feed stay usable.
- **KPI strip** (`components/KpiStrip.vue`, logic in `modules/kpiStrip.ts`): in the grid cell between the side panels over the 3D view (wraps onto more rows, never covered), count-up (ease-out 600 ms, skipped with reduced motion) and a pulse when a value crosses its threshold (`crossedThreshold`; thresholds are [A] illustrative). Values are fixed-width so the strip does not shift as they tick: counts show no decimals, rates and percentages always exactly one (`Formatter.fixed`, e.g. 12 reads "12.0 moves/h"), every value is tabular figures with a per-item `minWidthCh` (`tests/kpi-strip.test.ts`; width asserted in `terminal-twin-hud.smoke.ts`). The store polls `kpiHeadline` once a second when the event count changed and after reset/run-to/step, so the strip shows the engine's state, which runs up to the look-ahead ahead of the display while playing (equal when paused).
- **Export** (`engine/export.ts`): `kpiReportJson` (summary, series, headline, highlights), `kpiReportCsv` (long form: kpi, unit, entityKind, entity, bucket hour|shift|total, index, startS, endS, value), `eventLogJson`, `eventLogCsv` (payload and subjects as JSON cells). UI: report buttons download via the worker `export` request. CLI: `--kpi-json --kpi-csv --events-json --events-csv`.
- **Worker/dev API**: queries `kpiSeries`, `kpiHeadline`, request `export`; `__tt.exportRun(kind)`, `__tt.report()`, `load(name, {endConditions})`, `ui().reportOpen`. Smoke: `tests/browser/terminal-twin-kpi.smoke.ts`.

## Dashboard (TT-16)

- **What:** the full-screen tab (`B`, or the top-bar Dashboard button; `store.dashboardOpen`) in `components/DashboardTab.vue`. Tabs: **Charts** (KPI group selector Quay / Horizontal transport / Yard / Landside / TOS handlers, an hours or shifts toggle) and **Final report** (the TT-07 `FinalReport.vue` rendered with the `embedded` prop). When the run ends the dashboard opens itself on the report tab, once per run (`refreshKpis`); closing it docks the report panel over the 3D view as before. Reset and New Scenario close the dashboard. The Landside group only appears when a landside series exists; it charts the truck turnaround metrics (TT-R18, [yard-and-landside.md](yard-and-landside.md)) and adds a whole-run summary table.
- **Lazy loading:** `TerminalTwin.vue` loads `DashboardTab` with `defineAsyncComponent`, and the component loads `modules/chartLib.ts` (the only runtime importer of `echarts`, tree-shaken: line, heatmap and custom charts, grid/legend/tooltip/dataZoom/visualMap/aria, canvas renderer) with a dynamic `import()` when it mounts. Never import `echarts` or `chartLib` statically anywhere else (`tests/dashboard-lazy.test.ts` scans the sources; `terminal-twin.prod.smoke` / `terminal-twin-dashboard.prod.smoke.ts` checks the built output, where `chartLib-*.js` is its own chunk fetched on first open).
- **Data:** the worker query `dashboard` returns `DashboardData {series: KpiSeriesReport, timeline: TimelineReport, yard: {id, fillPct}[], landside: LandsideKpiReport | null}` in one round trip. The store keeps it in `dashboardData` and refetches (the KPI poll timer, once a second) while the dashboard is open and the event count changed. `dashboardGroup`, `dashboardBucketing`, `dashboardTab` are store state; `dashboardRendered` is what the component has drawn (for `__tt.dashboard()`).
- **Pure layers (test through these):** `engine/kpi/timeline.ts` `buildTimeline(events, now)` (Gantt rows from the event log: anchorage, mooring, work, unmooring per vessel and one work package per crane-split assignment, closed at `now` while open; exported from `engine/index.ts`); `modules/dashboardModel.ts` (`KPI_GROUPS`, `groupsWithData`, `buildGroupCharts`, `downsampleEvery`, `buildYardHeatmap`, `blockFillPct`); `modules/dashboardOptions.ts` (ECharts option builders, `import type` only from echarts, formatting passed in as `ChartFormat` from `store.fmt`); `modules/dashboardPalette.ts`.
- **Charts:** one line per entity (at most 8, the palette size, the rest counted as "N more not shown"); `sampling: 'lttb'`, `downsampleEvery` caps points at `POINT_BUDGET`; inside + slider data zoom; every chart has an HTML "Table view" of whole-run totals. The yard heatmap is block x hour (`yard.fill-pct` hourly, one-hue blue ramp, 0 to 100 %) with a "now" fill per block from the engine's stacked boxes. The Gantt is a custom series (one series per phase); an HTML legend carries the phase names and textures.
- **Palette and accessibility:** `SERIES_COLOURS` are the dataviz skill's light-surface categorical steps, validated with `validate_palette.js --mode light` on `#fcfcfb` (all checks pass: worst adjacent CVD dE 9.1, normal-vision 19.6; aqua, yellow and magenta sit under 3:1, which the relief rule covers through legend, marker symbols and the table view). `SURFACE` equals `--tt-chart-surface` in `skin.css` (tests/skin.test.ts). Do not reorder or recolour them without re-running the validator; the Gantt phases use the first five slots in order (validated as a set). State is never colour alone: every line slot also has its own marker symbol and dash (`SERIES_SYMBOLS`, `SERIES_DASHES`), a legend is always present, Gantt phases carry a texture as well as a colour, and the heatmap cells print their value. Charts are `role="img"` with `aria-label`; the aria option is on.
- **Catalogue:** all text is `dashboard.*` keys; each KPI title is `dashboard.kpi.<kpi id>` (`kpiLabelKey`). Adding a KPI to `KPI_DEFS` fails `tests/dashboard-model.test.ts` until it is in a group in `KPI_GROUPS` and has a title.
- **Dev API:** `await __tt.openDashboard({tab?, group?, bucketing?})` and `__tt.dashboard()`; `rendered` = `{chartLibLoaded, charts[{kpiId, lines, points, zoom, drawn}], heatmap{blocks, hours, values, liveFill}, gantt{rows, bars}, landside[{id, value, unit}] | null}`.
- **Smoke:** `tests/browser/terminal-twin-dashboard.smoke.ts` (lazy chunk, 24 h run + wheel zoom, heatmap vs `yardBlocks`/`yardSlots`, Gantt vs `vessels`, report tab) and `terminal-twin-dashboard.prod.smoke.ts`.


## SHC operational states and dispatch metrics (TT-R11)

`engine/shcStates.ts` maps every `ShcStatus` to one of seven operational states (`SHC_OPERATIONAL_STATES`); `shcOperationalState(shc, now)` is the one function the inspector uses. A status names the last phase event that fired, so the table maps what the SHC is doing next: `job-assigned`, `routing-to-parking` -> moving to collect (an assigned SHC whose trip starts later, for its reservations, is queuing to collect until then); `waiting-for-pad` -> queuing to collect; `routing-empty`, `positioning-at-pickup`, `locking` -> collecting; `lifting` -> moving to deliver; `routing-loaded`, `positioning-at-dropoff`, `lowering`, `unlocking`, `clearing` -> delivering; `parked`, `waiting-for-dispatch`, `available` -> parked. Queuing to deliver has no status yet (SHCs never wait mid-trip), so it stays 0 until queue areas exist.

The KPI collector derives the time in each state from the same events (no event-log change, no `ENGINE_VERSION` bump): `shc.state.<state>-s` series per SHC, `shc.handovers` (ShcPicked, ShcPickedAtWtp, ShcDroppedAtWtp, ShcDroppedAtGround), and `shc.empty-distance-m` (existing). `kpiReport().horizontal.shcs[id]` gains `stateS` and `handovers` (read from the collector over the measured period, so after a warm-up they cover the measured run); the headline adds `shcEmptyDistanceM`, `shcHandovers` and `shcStateS` (mean seconds per SHC). The CLI prints them per SHC and in the headline; the JSON export carries them in `kpis`, `series` and `headline`, the CSV in the series rows. The dashboard's horizontal group lists the new series; the inspector shows an "Operational state" fact first.

TT-R12 adds per-SHC `parkingReturns` (drives back to the parking spot) and `queueArrivals` (arrivals at a queue spot) to `kpiReport().horizontal.shcs` (engine counters, not collector series; the CLI prints them). Time waiting at a queue spot is in `queuing-to-deliver` (loaded) and `queuing-to-collect` (empty).

## Dwell by direction (spec #106, #109)

`KpiReport.dwell` is `Partial<Record<TransitDirection, { count, departed, meanS, maxS }>>`, built in `buildKpiReport` from the containers (`dwellS` in `engine/transit.ts`): arrival on the terminal to departure from terminal custody, or to now for a box still here. Directions with no arrived box are omitted. It is a report field only (no collector series, no dashboard tile yet); the CLI prints it under `Dwell on terminal:`. Boxes restored from a snapshot that predates `props` are skipped.
