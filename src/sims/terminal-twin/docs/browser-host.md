## Browser host (TT-02)

- **Threads.** The engine runs in a Web Worker (`worker/engine.worker.ts`), driven only through the public engine API (`runUntilAsync`, `step`, `query`, `inject`, …). The main thread renders and runs the UI. The worker answers each request with a **Delta**: new motion plans per STS (diffed by `StsState.motion` identity), custody changes (with the grounding X for ground positions), hatch panel changes (`Delta.hatch`, TT-R10), STS/vessel status changes, the last 200 summarised events, and per-type counts. It also sends `EngineInfo` (engine time, status, end time, moves, hash).
- **Playback clock** (`TwinController`). `displayTime` advances by wall time × speed. It is clamped to the **engine horizon** (`info.now`) and to the scenario end. While playing, the controller keeps the engine a look-ahead ahead (`max(5 s, 1.5 s × speed)`) with `advance` requests, so the motion segments for the displayed instant are already known. That keeps animation smooth up to ×3600 (twelve steps, `SPEEDS`). **While paused it does not run ahead**, so the scene and dev-API queries describe the same instant.
- **Flat-out runs.** "Run to…", `__tt.runUntil` and `__tt.step` send `run`/`step`. Rendering is skipped while `busy`. The delta is compacted to the latest plan, custody and status per entity, and the display jumps to the target (Run to…) or to the engine time (runUntil/step, which also pause). The Run to… popover also has "Next vessel departure" (`TwinController.runToNextDeparture`, `store.runToNextDeparture`, `data-testid="tt-run-to-departure"`): flat out to the next `VesselDeparted` the engine has not yet processed (the engine may be a look-ahead ahead of the display), then playback resumes.
- **Scene model.** `SceneModel` keeps per-axis segment lists and custody/status timelines and prunes history older than the display time. `positionAt` interpolates the crane, and a carried box follows the spreader. Display time never goes backwards, except on reset/load, which build a new model; a generation counter drops replies that belong to the old scenario.
- **Rendering.** Containers are drawn by `ContainerInstancer`: procedural boxes until the GLBs load, then one `InstancedMesh` per size × LOD with a livery per instance (see [Phase 2 asset pipeline](assets-pipeline.md#phase-2-asset-pipeline)). STS, hulls and the quay are shared low-poly boxes. Three.js objects never enter Vue reactivity; the store mirrors only the clock, speed, engine info and selection.
- **Setup dialog layout (#161).** About 90vw wide (max 1440 px, `width: min(90vw, 1440px, 100%)`), height capped to the sim area; the dialog never scrolls, only the tab body (`tt-setup-body`) does. Four tabs (`role=tab`, `tt-setup-tab-<scenario|vessels|yard|advanced>`, Left/Right arrows move between them; panels `role=tabpanel` with `data-setup-tab`, all mounted with `v-show` so the draft and the inputs persist): **Scenario** (the picker and detail below; on a wide screen they fill the tab and scroll on their own), **Vessels** (`SetupVesselsSection`: vessel table, transshipment and empties), **Yard and equipment** (layout, STS, landside, SHC, yard, modes), **Advanced** (`tt-advanced`: seed and start, end conditions, display, decisions). A footer pinned to the bottom (`tt-setup-footer`) holds the selected scenario's plain name (`tt-setup-footer-name`, with `data-scenario`), Cancel (when a scenario is loaded) and the one Start button (`tt-setup-start-button`, `type=submit`, so Enter in a field still submits). The hero picture shows only on screens taller than 820 px and wider than 760 px. **Validation on tabs:** `modules/setupTabs.ts` (`CHECK_KEY_TABS`, `tabOfCheckKey`, `setupIssues`, `tabsWithIssues`; `tests/setup-tabs.test.ts`, which also fails on a new `setup.check.*` key without a tab) places every problem (section validators, scenario checks, end conditions) on the tab that holds its field; each panel lists its own problems and warnings live (`tt-setup-issues-<tab>`), a tab with a problem is marked (red, alert icon, `data-has-error`, aria-label "(needs fixing)"), and the footer says which tabs to fix (`tt-setup-footer-fix`; an engine start error shows there as `tt-setup-error`). The form is `novalidate`: Start opens the tab of the first input the browser rejects (min, max, required) and reports it there, else the tab of the first problem. Smoke helpers: `openSetupTab(scope, tab)` and `openAdvanced` in `tests/browser/scenarioPicker.ts`; a spec that edits a field opens its tab first (fields in hidden tabs cannot be filled).
- **Setup dialog.** Start screen (#145, was TT-R04): **Scenarios** and **Test benches** tabs with data-driven counts, a list of plain names (benches under 5 headings) and a detail pane (Start is in the footer since #161) (`setup/ScenarioPicker.vue`, `setup/ScenarioDetail.vue`, `setup/LayoutSketch.vue`; chips, sketch and run length derived from the config by `modules/scenarioPicker.ts`: `scenarioStats`, `statChips`, `layoutSketch`, `scenarioDurationS`, `pickerModel`). Fixture names and descriptions come from `scenario/fixtures/definitions.ts` (`fixtureCopy`), preset copy from the `preset.*` catalogue keys via `presetCopy`. Rows (`role=radio`, `tabindex=0`) select with Enter, Space or click. A fresh load selects the TTI Algeciras baseline preset (`DEFAULT_SCENARIO_NAME`) with its own seed and opens on Scenarios (#156). Only plain names are shown (`scenarioDisplayName`); technical ids live in `data-scenario` on the rows and the detail pane, the dev API and the logs, and default save names and download file names are built from the plain name (`defaultSaveName`, `exportFileName` in `persistence/saves.ts`). Seed (re-roll), start date/time (default Monday 08:00 of the current week, local time) and end conditions live on the Advanced tab (`tt-advanced`; seed and start in `setup/SetupSeedStart.vue`). Start = `store.startScenario({ name, seed, startDateTime })`. The start date changes only the clock, not the run. Smoke helpers: `tests/browser/scenarioPicker.ts` (`pickScenario` opens the Scenario tab, then the picker list that holds the name; `openSetupTab`, `openAdvanced`); test ids `tt-tab-*`, `tt-count-*`, `tt-preset-card`, `tt-fixture-row` (both carry `data-scenario`), `tt-chip-*`, `tt-detail-*`, `tt-scenario-detail` (with `data-scenario`). A spec that presses Start on a fresh load runs the TTI baseline unless it picks a fixture with `pickScenario` first.

- Browser: `runUntil({ time })` leaves `now = time`, so the engine horizon is exact. Playback in time slices gives the same hash as one run (`tests/live-driving.test.ts`).
- Browser: injected events are extra roots, so `why` on them (or their descendants) ends at the injected event, not at `ScenarioStarted`.
- Browser: deltas in a flat-out run are compacted per entity. Large Run to… jumps at TTI scale may still need a smarter "final state only" message (TT-19).
- Smoke tests: `playwright.config.ts` starts a Vite dev server (port 5199) and builds plus previews production (`.smoke-dist/`, port 5198) every run. Chromium falls back to `/opt/pw-browsers/chromium` like `pnpm run screenshot`.
- Three objects never go into Vue reactivity (`markRaw` or module scope), and large collections live in `shallowRef(markRaw(...))` plus one `triggerRef` per frame. The shared `src/composables/useThreeScene.ts` is too limited for the twin (far plane 1000, no OrbitControls, deprecated `THREE.Clock`), hence `composables/useTwinScene.ts`.
- Worker build: `vite.config.ts` sets `worker.format = 'es'`; the worker must not import `three`; create it as `new Worker(new URL('./engine.worker.ts', import.meta.url), { type: 'module' })` (the URL literal in the same expression); the worker entry carries `/// <reference lib="webworker" />`.
- Design tokens: the sim uses the `src/assets/main.css` tokens but must not use `--font-retro` (Press Start 2P); there are no mono, warning or spacing tokens, so define sim-local ones.
- Smoke specs import JSON with `with { type: 'json' }` (Playwright ESM); frame-count assertions (for example at least 10 frames/s) can fail when the machine is busy: rerun on a quiet machine.

### Locale, units, message catalogue, shortcuts (TT-20)

- **Message catalogue.** Every user-visible string in the sim's `.vue` files comes from `i18n/messages.ts` via `t('key', { param })`. `tests/message-catalogue.test.ts` parses every SFC (template text, `title`/`aria-label`/`placeholder`/`alt`/`label`, string literals in `<script>` and template expressions that read as UI text) and fails on hard-coded text. Add the key first, then use it. Ids, fixture names and engine values are data, not text.
- **Display settings** (`DisplaySettings {locale, units}`, type in `scenario/types.ts`): `store.display`, `store.fmt` (a `Formatter`), `store.setDisplay(partial)`. They default from `navigator.languages` on first open (US region → imperial, else metric; bare `en` → US), are remembered in `localStorage` (`terminal-twin.display`), and are written into the run's config as `config.display` (`store.config`, the SI config a save should store). Changing them applies live (the setup dialog's select/radios call `setDisplay` immediately; Cancel keeps them).
- **Units are display-only.** Engine, configs, snapshots stay SI. Format with `store.fmt.length(m)`, `.speed(m/s)` (km/h or **mi/h**; never "mph", which means crane moves per hour), `.mass(t)` (t or US tons), `.number(n, digits)`, `.movesPerHour`, `.teu`, `.clock(startIso, t)`, `.dateTime(date)`, `.firstDayOfWeek()`, `.weekdayName(d)`. Never format numbers or dates with `toFixed`/`toLocale*` in components.
- **Location notation (TT-R08):** the inspector shows slots in maritime notation through `store.locations` (`modules/locationNotation.ts`): the container "Held by" fact and custody history (`Fact.owner`, `CustodyRow.size`) and a `tt-event-locations` list under the raw event payload (which stays the engine's JSON). Vessel number and yard block number are the id's trailing digits. The feed, labels and 3D picking show entity ids only, no slots.
- **Shortcuts** (`modules/shortcuts.ts` table → `composables/useTwinShortcuts.ts`): Space pause/resume, 0 = pause (no key changes speed: the digit keys 1 to 9 were unbound in #138, use the top bar buttons or `__tt.setSpeed`), `.` single-step (`store.step()`, pauses), F follow selection (`store.following`; the scene loop re-aims the camera each frame), Esc closes help else deselects (stops following), B `store.toggleDashboard()` (moved from D in TT-R03, which the camera keys took) (the dashboard tab, TT-16), O `store.overlaysVisible` (master switch of the TT-18 overlays, plus a toast), E / I toggle the event feed and inspector panels (TT-18), N follow the next truck (V11-06, below), Q / Y / G / V view presets (V11-05, below), `?` help overlay (`store.helpOpen`; also the top bar `?` button), and the held camera keys (below). Ignored with Ctrl/Meta/Alt, in inputs/selects/textareas/contenteditable, on key repeat (except `.`), and while the setup dialog is open. Space calls `preventDefault` so a focused button is not also clicked. The help overlay renders `SHORTCUT_HELP`, so add new shortcuts there.
- **God mode:** the shared `useGodModeHotkey` ("god" typed anywhere) is not mounted by Terminal Twin. Don't add it: its `o`/`d` keys would also toggle overlays and the dashboard.

- Locale-aware date entry (V11-17): setup start, the vessel arrival/first-arrival fields and Run to… use `components/LocaleDateTimeInput.vue`, a text field that shows and parses the *chosen* locale's order, separators and 12/24 h (`i18n/dateInput.ts`: `formatDateInput`, `parseDateInput`, `dateInputPattern`, built from `Intl.DateTimeFormat#formatToParts`). The model stays the local ISO string (`modules/time.ts`); unparseable text emits `''` and sets `aria-invalid`. Never use `datetime-local` (it follows the browser's locale, not ours). Test ids: `tt-setup-start`, `tt-run-to-input`.
- ICU differences: `de` weekday "Mo" vs "Mo." (match loosely in tests). Node 22 lacks `Intl.Locale#getWeekInfo`, so `i18n/format.ts` falls back to a region table.

### Dev API (`window.__tt`, dev builds only)

`dev/devApi.ts` is dynamically imported inside `if (import.meta.env.DEV)`, so production builds don't contain it (checked by `terminal-twin.prod.smoke.ts`). Every call is async-safe from `page.evaluate`:

```js
await __tt.load('tracer-1sts-10-boxes', { seed?, startDateTime?, autoplay?, overrides? })  // default: fixture's own seed, paused
await __tt.runUntil({ time?, eventType?, moves?, vesselsCompleted?, maxEvents? }) // no arg = to the end; pauses
await __tt.runTo(600); await __tt.step()
await __tt.query('summary' | 'kpis' | 'containers' | 'stsList' | 'vessels' | 'vesselSlots' | 'invariants' | 'eventLog')
await __tt.query('container' | 'vessel' | 'sts' | 'groundPosition', id)
await __tt.inject('VesselBerthed', 120, { vessels: ['V001'] }, { vesselId: 'V001', berthX: 50 })  // new root event
await __tt.snapshot(); await __tt.why(eventId)
__tt.select(id | null); __tt.cameraTo(id); __tt.setSpeed(600); __tt.pause(); __tt.play(); await __tt.reset(); __tt.newScenario()
await __tt.query('shc' | 'wtpPad', id); await __tt.query('shcList' | 'reservations')
__tt.overlays({ laneGraph?, reservations?, occupancy?, labels? })   // toggles 3D overlays, returns the state
await __tt.load('shc-1sts-2shc-1wtp', { shc: { count: 3, kinematics } })  // SHC fleet override, like the setup dialog
__tt.clock()       // { displayTime, speed, paused, busy, engine: EngineInfo }
__tt.scene()       // rendered { containers, sts, shcs, vessels, overlays, reservedZones, frames,
                   //   containerLods: { lod0, lod1, closeup, culled }, containerAssets: 'placeholder'|'loaded',
                   //   shcLods: { lod0, lod1, lod2 }, shcAssets: 'placeholder'|'loaded',
                   //   ascLods: { lod0, lod1, lod2 }, ascAssets: 'placeholder'|'loaded' }
__tt.sceneState()  // what the scene shows: custody per box, status + pose per STS and SHC, status per vessel,
                   //   active reservations, liveries: { [containerId]: { index (atlas tile), size, lod } } as drawn,
                   //   shcRigs: { [shcId]: { lod, steerRad, wheelRollRad, hoistM, carrying } } as drawn,
                   //   ascRigs: { [ascId]: { lod, gantryZ, trolleyX, hoistM, ropeScale, scaleY, carrying } } as drawn
__tt.followNextTruck()  // select and follow the next truck to arrive at or after the display time (V11-06); its id, or null while none is known yet (ui().followNextPending stays true until it resolves)
__tt.viewPreset('quay' | 'yard' | 'gate' | 'overview')  // frame a view preset (V11-05); false for an unknown name or no landside (gate)
__tt.cameraTo(id, distanceM?)  // aim at any entity the inspector shows (also a block, transfer stall, WTP pad, 'gate'; returns false for an unknown id and for a truck that has not yet arrived or has already left, by design: follow releases at that point), optionally from a distance (60 → LOD0, 600 → LOD1)
__tt.display(); __tt.setDisplay({ locale: 'de-DE', units: 'imperial' })  // live locale/units
__tt.config()      // loaded scenario config (SI) + current display settings
__tt.ui()          // { selectedId, following, overlaysVisible, dashboardOpen, helpOpen, feedOpen, inspectorOpen }
__tt.dashboard()   // { open, tab, group, bucketing, rendered } (TT-16); await __tt.openDashboard({ tab, group, bucketing })
await __tt.addBreakpoint('eventType' | 'container' | 'equipment' | 'decision', value); await __tt.removeBreakpoint(id); await __tt.clearBreakpoints(); __tt.breakpoints()
await __tt.inspectEvent(eventId)   // opens the inspector on the event and its cause chain
__tt.debug()       // { breakHit, paused, inspectedEvent: { id, type, chain: [{id, type, causedBy}] }, entity: { kind, id, status } }
__tt.hudLayout()                                       // bounding box of each named HUD region (null when hidden)
__tt.screenPoint(id); __tt.pickAt(clientX, clientY); __tt.cameraPose()   // 3D picking (client coordinates) and the orbit camera: { target: {x,y,z}, distance, azimuth, polar } (TT-R03; replaces cameraTarget)
```

## Debugger and inspection UI (TT-18)

- **Panels.** `E` toggles the left panel (`EventFeedPanel`: Step, Continue, breakpoints, filter, event feed), `I` the right panel (`InspectorPanel`). Both start collapsed. Clicking something, or a breakpoint hit, opens the inspector. They overlay the 3D view (the canvas is not resized). The top bar has a Step button as well as `.`.
- **Breakpoints** (`modules/breakpoints.ts`): on an event type, a container id, an equipment id or a decision point (matches `DecisionRequested/Resolved/Failed` of that point). The list lives in the store and is sent to the worker (`setBreakpoints`), which keeps it across load/reset. `eventMatchesBreakpoint` is the stop `predicate` of every `advance`/`run`/`step`, so the engine stops right after the matching event and `Delta.breakpoint` names it. The controller keeps it as `pendingBreak` until the display reaches that event (look-ahead), then pauses with `breakHit` set, and the store opens the inspector on it. `play()`, a speed button, Run to… and step clear `breakHit`. A breakpoint added while the engine is already ahead of the display (look-ahead, at most `max(5 s, 1.5 s × speed)`) only catches events that have not been processed yet.
- **Single-step** is one engine event per press at any speed (it pauses). The inspector shows the stepped event. With the engine ahead of the display after a pause, the display jumps to that event's time (see the debugger gotchas at the end of this section).
- **Event feed** (`modules/eventFeed.ts`): the store keeps the last `FEED_BUFFER_CAP` (1000) summarised events; the panel rebuilds its rows every `FEED_REFRESH_MS` (250 ms, never per frame), shows only events up to the display time, newest first, at most `FEED_MAX_ROWS` (150). From ×60 (`FEED_SUMMARY_MIN_SPEED`) while playing, runs of three or more events of one type collapse into a "N × Type" row. The filter takes space-separated terms that must all occur in the event type or a subject id.
- **Event inspector** (`modules/eventInspector.ts`): payload (motion segments summarised), clickable subjects, and for decision events the handler, outcome, request and reply. The cause chain comes from the engine's `why` through the worker (`op: 'why'`), newest first and ending at the root `ScenarioStarted` (or an injected root); clicking an entry shows that event while keeping the chain.
- **Selection** (`modules/picking.ts`): `entityBounds(model, id, t)` gives each container, SHC, ASC, STS and vessel an oriented box (also the selection outline). `pickEntity` returns the nearest container the ray hits, else the nearest equipment or vessel (their boxes enclose their boxes). A click (under 5 px and 600 ms) selects; a click on nothing deselects; dragging orbits as before. `store.select(id)` opens the inspector and `refreshEntity()` queries the engine (`container`, `sts`, `shc` + `shcJobs`, `asc`, `vessel`); the inspector refreshes twice a second. It shows the engine's state (which may be slightly ahead of the display while playing); the container custody history is the engine's full history. For equipment and vessels, "history" is the recent events that name the id (from the feed buffer).
- **Follow camera.** The Follow button in the inspector or `F`. The scene loop re-aims the orbit target at the selection every frame, keeping the viewing offset.
- **HUD regions** (`modules/hudLayout.ts`): `.scene` in `TerminalTwin.vue` is a grid (`auto | 1fr | auto` columns and rows). Each region's root element has `data-hud-region`: `topBar` and `settings` (siblings inside `TopBar.vue`; settings = Daylight, Sound, Quality, Stats), `kpiStrip` (centre column, top; wraps), `leftPanel` (Events) and `rightPanel` (Inspector) (full-height side columns, as wide as their tab or body), `overlayBar` (centre column, bottom). Regions never overlap: `overlappingRegions(__tt.hudLayout())` is the rule `terminal-twin-hud.smoke.ts` asserts for every preset at 1280x720 and 1920x1080 with both panels open or closed. Add new HUD elements as a grid cell or inside a region, never `position: absolute` over one. `.scene` uses `flex: 1 1 0px` so a side panel's content cannot stretch it. Active toggles show a check mark (state by shape, not colour alone). The shared sim header (`SimPage.vue`) shows one "MENU" label.
- **Follow next truck** (V11-06): the "Follow next truck" button in the overlay bar region (`data-testid="tt-follow-next-truck"`, pressed while pending), `N` and `__tt.followNextTruck()` call `store.followNextTruck()`. It records the display time, and `SceneModel.nextTruckArrival(time)` (arrival time = a truck's first status entry, kept until the truck is pruned) names the earliest known arrival at or after it. If the engine knows none yet (paused at the start), the request stays pending (`store.followNextPending`) and `store.sync()` resolves it as the engine runs on. Resolving selects the truck, turns follow on and aims at the gate. While `SceneModel.truckPhase` is `waiting` the follow loop keeps the camera still; once the truck is `gone` (left, or pruned) the loop releases follow as before. Deselect, F, a view preset or a new request cancel a pending request. No landside: a toast and nothing else. `tests/follow-next-truck.test.ts`, `tests/browser/terminal-twin-follow-truck.smoke.ts`.
- **Keyboard camera** (TT-R03): W/↑ S/↓ pan forward/back along the camera heading on the ground plane, A/← D/→ pan left/right; with **Shift**, A/D or ←/→ orbit (azimuth; right = camera moves right) and W/S or ↑/↓ tilt (W = toward top-down), within the existing polar limit; `=`/`+`/numpad + zoom in, `-`/numpad − zoom out within `minDistance`..`maxDistance`. These are held-key state, not key repeat: `useTwinShortcuts` adds the key to `store.cameraKeys.held` on keydown (repeats ignored, `preventDefault` so arrows do not scroll), deletes it on keyup (matched by camera key, so releasing Shift first is harmless) and clears all on window blur or unmount; `store.cameraKeys.shift` follows every keydown/keyup. Each frame `useTwinScene.applyCameraKeys` turns the held set into a `CameraMotion` (`cameraMotion`), reads the orbit camera as a `CameraPose`, steps it with `stepCameraPose` (pure, `modules/cameraKeys.ts`; time-based with dt capped at 0.1 s, so speed is frame-rate independent; pan speed is 0.8 × distance per second, so it scales with zoom) and writes it back. Camera keys never fire while focus is in an input/select/textarea, and with Ctrl/Meta/Alt held; the first press of a camera key calls `store.releaseFollow()` (ends follow mode and a pending follow-next-truck). `__tt.cameraPose()` (dev API, replaces `cameraTarget()`) returns `{ target, distance, azimuth, polar }` (radians; polar is from straight up). `tests/keyboard-camera.test.ts`, `tests/browser/terminal-twin-keyboard-camera.smoke.ts`.
- **View presets** (V11-05, `modules/viewPresets.ts`): `viewPresetPose(model, preset, aspect)` returns `{ region, target, distanceM, direction }` computed from the layout (quay = STS extent plus a margin and the water side; yard = blocks' bounding box; gate = gate, roads and stalls; overview = union), or null (no landside for `gate`). The target is the region centre, so it lies inside the region; the distance fits the region to the window aspect. Q / Y / G / V (in `SHORTCUT_HELP`, same ignore rules as every shortcut), the View buttons in the overlay bar region (`data-testid="tt-view-<preset>"`; no new HUD region, so the no-overlap spec holds) and `__tt.viewPreset(name)` all call `store.setViewPreset`, which also releases follow. `tests/view-presets.test.ts`, `tests/browser/terminal-twin-views.smoke.ts`.
- **Label declutter** (V11-05, `modules/labelDeclutter.ts`): with Labels on, `OverlayLayers.update` projects each label to a screen box (world size 36 x 8 m, so labels shrink with distance), lays them out in priority order (selected entity, then registry order) and hides any that overlaps a kept one (`scene().layers.labelsHidden`; `labelBoxes` are the visible ones in px, which the smoke spec asserts do not overlap on the TTI Overview).
- **Overlays** (`modules/overlays.ts`, `OverlayToggles.vue`): `laneGraph`, `reservations`, `occupancy`, `labels`, independent of each other; `O` is the master switch. Occupancy tints WTP pads free/occupied and marks boxes standing on STS ground positions; labels float above each STS, SHC, ASC and berthed or anchored vessel with its status. Both read the `SceneModel` at the display time (`OverlayLayers`), and `scene().layers` reports the counts for tests. An overlay for the ASC reserved rail segments is not built: the ASCs (TT-06) do not reserve rail segments yet, so add it with the ticket that introduces them.
