# Terminal Twin: performance, quality and atmosphere

Engine benchmark, graphics quality settings and renderer budget; time of day, backdrop, sound and polish. Guide: [terminal-twin-AGENTS.md](../terminal-twin-AGENTS.md). Terms: [GLOSSARY.md](../../../../GLOSSARY.md).

## Performance and graphics quality (TT-19)

### Engine benchmark (local only, not in CI)
- `pnpm run tt:bench` runs the TTI preset for 24 sim-hours headless in one-hour slices and prints events/sec, wall-ms per sim-hour, peak memory (process RSS) and the machine (node, CPU, load average). It compares with `perf/baseline.json` and exits 1 on a **regression: any metric more than 20% worse**. Options: `--preset "TTI Algeciras, peak day"`, `--hours n`, `--sweep-every n` (full invariant sweep interval; 0 = invariants off), `--update-baseline` (records the run under `<preset>|<hours>h`), `--out report.json`, `--slow-ms n` (busy-waits n ms per event: the self-test that proves the flag trips).
- Code: `cli/benchmark.ts` (`runBenchmark`, `compareToBaseline`, `formatReport`), `cli/benchCli.ts` (`benchMain`), `tests/benchmark.test.ts` (a deliberately slowed engine trips the flag).
- Timings only compare on a like machine and a like load: re-record with `--update-baseline` when the reference machine changes, and check the recorded `load1` before blaming code for a regression. Baselines were recorded on a shared 4-vCPU Xeon container at load 4-6, so they are conservative (slow).
- **Recorded (24 sim-hours, `pnpm run tt:bench`, incremental invariants with a full sweep every 1000 events, the same as the worker, after #78):** TTI baseline 38,164 events in 18.5 s wall, about 2,060 events/s, about 770 ms per sim-hour, 538 MB peak RSS, 0 invariant violations. Invariant time is its own line: 8,549 ms in total (224 us per event, 38,125 incremental checks and 40 sweeps), a part of the wall time. **Measured with load average 5.85 on a 4-core machine, so re-measure on a quiet machine before trusting the figure;** `perf/baseline.json` still holds the older run (28,938 events, 1,700 events/s, 710 ms per sim-hour, 434 MB) and the bench flags the memory growth against it until it is re-recorded. The scenario now has more events than that older run, so the runs are not like for like. **TTI Algeciras, peak day** (older run, invariants every 144 events, not re-measured): 78,057 events, about 840 events/s, about 3,900 ms per sim-hour, 757 MB peak, status ready, 0 invariant violations and no engine error.
- **What the benchmark found and fixed:** the TTI preset ran about 20 events/s in the browser worker (one sim-hour took 147 s). Two causes: (1) rehandle helpers (`boxesAbove`, `vesselBelow`, `retrievalRanks`) scanned all ~28,000 yard slots per call, now served from `engine/yardIndex.ts` (per-block and per-column lists, kept current by `indexYardSlotAdded` / `indexYardSlotRemoved` at the three places slots are added or removed; any new code that adds or deletes `state.yardSlots` entries MUST call them); (2) the invariants scan the whole state, ~50 ms per event at TTI scale. **Superseded by V11-18:** the sparse `suggestedInvariantEvery` cadence is gone. Every event is now checked incrementally (only the invariants and entities it touched) and a full sweep runs every `sweepEvery` events (default 1000) and at the end of each run, in the worker, the CLI, the benchmark and the tests alike, so the exact-event guarantee holds again for everything an event names. `tt:bench` reports invariant time on its own line (a part of the wall time above). Golden hashes did not change.
- Still hot at TTI: `eligiblePickups` / `scanPickups` in `subsystems/landside.ts` scan every yard slot for each truck arrival (about 35% of the run); an index of pickup-ready boxes is the next win.

### Quality settings and the overlay
- `modules/quality.ts` (pure): `QUALITY_PROFILES` low / medium / high, `AutoQuality`, `FpsMeter`. A profile sets: sun shadows on/off and map size, container LOD0 distance and cap, `lodScale` (multiplies the STS / SHC / ASC LOD switch distances), render resolution scale (of the device pixel ratio, cap 2), ocean detail (grid segments; low is a flat Lambert quad), and `nightLights` (how many high-mast glow points night mode draws, applied by `AtmosphereRig.setQuality`, which also owns the sun-shadow switch: the sun casts shadows only when both the time of day and the quality allow it).
- Setting: Low / Medium / High / **Auto (default)**, remembered in localStorage (guarded). `store/perfStore.ts` holds setting, effective level, live stats (fps, draw calls, triangles, frame CPU ms, pose ms) and the overlay switch. `useTwinScene` measures every rendered frame, feeds `AutoQuality`, applies the effective profile (renderer shadow switch, pixel ratio, `SceneRenderer.setQuality`) and reports stats four times a second.
- **Auto:** steps down one level when 4 consecutive one-second windows are under 45 fps; steps up when 8 windows are at 57 fps or more; a step up that is undone within 30 s doubles the wait for the next one (max 240 s) so it does not oscillate; a frame gap over 1 s (hidden tab, long pause) is ignored. History restarts after every change.
- UI: `components/PerfPanel.vue` (in the top bar's settings region, beside Daylight): quality picker and a Stats button (key **P**) that shows FPS, draw calls, triangles, frame CPU ms and the quality in force. Draw calls and triangles come from `renderer.info` and include the shadow pass.
- Dev API: `perf()`, `setQuality(setting)`, `perfOverlay(on)`, `setFrameLoad(ms)` (busy-wait per frame), `setAutoThresholds({down, up})` (headless software rendering cannot reach 45 / 57 fps), `drawBreakdown()` (which scene groups cost the draw calls).

### Renderer budget
- **Culling:** `ContainerInstancer.end(camera, frustum)` skips boxes outside the camera frustum (per-instance sphere test; the InstancedMesh itself is never culled); `containerLods.culled` in `scene()` counts them. Everything else uses Three's own frustum culling.
- **Batching:** static scenery (yard slabs, ASC rails, bay ticks, stall and pad markings, road surfaces, gate buildings) goes through `modules/staticBatch.ts` and is merged per material: the TTI overview went from 1,563 to 265 draw calls (including the shadow pass). New static scenery should use `StaticBatch`, not one mesh per piece.
- `SceneModel.containerPose` caches the pose of stacked boxes (`yardPoses`); treat the returned object as read-only.
- **Measured (TTI preset, overview at 1,100 m from STS104, High, headless SwiftShader):** 10,151 containers, 265 draw calls, 307k triangles, scene posing about 10 ms per frame (inflated, the container shared four cores with the software rasteriser and other agents). Zoomed in on one crane over 80% of the boxes are culled.
- **Frame-rate target and the reference machine:** 60 fps for the full TTI preset at overview zoom on a **mid-range laptop: a 4-core CPU of about 2020 (e.g. Core i5-1135G7 or Apple M1 class) with an integrated GPU (Intel Iris Xe or similar), 16 GB, Chrome, a 1080p window, the engine in its worker**. Budget that follows: at most about 300 draw calls and 400k triangles in the main plus shadow pass, and under about 8 ms of main-thread time per frame for posing. **Unmet here, and why:** this container has no GPU (WebGL is software rendered at about 1 fps), so no real frame rate could be measured. The numbers above are the proxies that were measured; read the real figure from the in-app overlay on the reference machine (press P, TTI preset, zoom out). Auto holds 45 fps or better by stepping quality down. Record the observed fps here when someone has done that.
- **Measured on real hardware (V11-19, #79; 2026-10-29):** Windows 11 laptop, Intel Iris Xe (ANGLE D3D11), 8 logical cores, display scale 1.25, in-app browser pane 1024x768, **Vite dev server** (unminified, so main-thread time is pessimistic; re-check on a production build), engine in its worker. TTI preset run to 04:00 sim time (10,110 containers, none culled, all LOD1), paused, overview camera `cameraTo('STS104', 1100)`, 8 one-second samples per setting from the P overlay (`__tt.perf()`):

  | Setting | fps | draw calls | triangles | frame CPU ms | pose ms |
  |---|---|---|---|---|---|
  | Low | 30 | 246 | 834k | 16.7 | 13.3 |
  | Medium | 30 | 281 | 1.57M | 17.8 | 13.8 |
  | High | 29.9 (min 29.5) | 286 | 1.58M | 20.3 | 16.1 |
  | Auto | 30 (stepped high > medium > low, 4 changes) | 269 | 1.30M | 17.3 | 13.5 |

  **The 60 fps target is not met: every setting sits at 30 fps.** The cause is the main thread, not the GPU: frame CPU time is 17-20 ms (over the 16.7 ms vsync budget, so frames quantise to 30 fps) and scene posing alone is 13-16 ms against the 8 ms budget, while Low cuts triangles in half and changes neither fps nor pose time. Draw calls are within the 300 budget; triangles are not (1.6M against 400k at Medium/High). Auto churned down to Low without gaining fps, because the quality steps do not touch posing cost. Next win: cut `SceneModel` posing for the ~10k stacked boxes (cache or skip unchanged poses; cull before posing), and cut triangles with a lower container LOD at overview distance.
- **Screenshots (#123):** the default camera (low, from the apron facing the water: Rock, shore strip and anchored ships on the horizon), the overview (road, rail and warehouses along the landside, ships at anchor) and a quay-level pose were reviewed against the reference aerial of the bay and the view from the Algeciras hills; the shore, anchorage and landside read as in the references, the tanks and town sit out of the default frame (they show from the landward views).
- **Surroundings cost (#123; TTI baseline preset at 08:00, High, headless SwiftShader at about 0.3 fps, so only draw calls and triangles mean anything; CPU and pose ms below are software-render noise):** before the surroundings, whole terminal in view (`cameraTo('STS104', 1100)`): 277 draw calls, 1,578,380 triangles, frame CPU 88.9 ms, pose 55.2 ms; default camera: 717 calls, 1,870,172 triangles. After: overview 282 calls (+5), 1,584,449 triangles (+6,069, +0.4%), frame CPU 71.8 ms, pose 40.1 ms; default camera 721 calls (+4, the Rock-side parts are in frame), 1,875,623 triangles. The five scenery meshes are static, unlit by shadows (no cast or receive), frustum-culled and share the infrastructure atlas material, so they add no per-frame posing. No meaningful regression; a real-GPU number is still to be read from the P overlay on the reference machine.
- Smoke: `tests/browser/terminal-twin-perf.smoke.ts` (overlay, Low vs High draw calls, Auto step down and recovery with retuned thresholds, TTI overview budget and culling).

## Atmosphere and polish (TT-21)

| Piece | Where | Notes |
|---|---|---|
| Time of day | `modules/atmosphere.ts` (`hourOfDay`, `lightingFor`, `daylightLockDefault`) | Local hour of the sim clock (same zone as the clock display). Sun 06:30 to 19:30, modes `day` / `dusk` / `night`. `lockDaylight` squeezes the 24 h into the daylight window: the sun still travels, night never falls. Default on where the terminal's preset says so (`daylightLockDefault` on its `TerminalPresetInfo`; TTI peak day) (`store.lockDaylight`, top-bar Daylight button). |
| Lighting rig | `modules/atmosphereRig.ts` (`AtmosphereRig`, owned by `SceneRenderer`) | Sun, hemisphere, sky/fog colours. Night is the cheaper mode: sun shadow pass off, no extra real lights; high-mast poles (instanced, always drawn) get additive glow points and every STS/ASC/SHC gets one glow point (2 draw calls in all). `useTwinScene` re-applies lighting when the clock crosses a minute or the lock flips. |
| Backdrop | `modules/backdrop.ts` (`sceneryFor`, `buildBackdrop`, `backdropModelAssets`, `GENERIC_SCENERY`) | Which scenery a scenario gets comes from the terminal registry (`terminals/`, see below), never from a preset-name comparison in `backdrop.ts`. A scenario owned by TTI Algeciras gets `tti` scenery (`terminals/tti-algeciras/scenery.ts`): the Rock of Gibraltar at true scale, Algeciras hills, the 550 m North Quay (bare slab, no equipment, no lights). Every other scenario (generic presets, fixtures, custom): the `generic` coastline, no TTI scenery. Flat-shaded, no textures. Water, land and the camera far plane (14 000 m) were enlarged for it; the fog far distance is the scenery's own `fogFarM` (generic 9000 m, TTI 24 000 m so the Rock at about 9.2 km is hazy, not erased). |
| Cues | `modules/cues.ts` (`CuePlanner`, `SoundThrottle`, `minGapMs`) | Events to cues: `StsGrounded`/`StsLoaded` landed, `VesselArrived`/`VesselDeparted` horn (departure also a banner), `ScenarioEnded` chime. Released when the DISPLAY clock reaches them; long-past cues (a Run to… jump) are dropped. |
| Sound | `modules/soundPlayer.ts`, `assets/sounds/*.mp3` (copies from `available-media/sound-samples`) | Terminal Twin has no sound toggle of its own: `SoundPlayer` takes one master gain, the shared `useAudioStore().masterGain` (volume, 0 while muted; default unmuted at 40%, and a mute set in another sim is honoured). Each sound plays at its base level times the gain, a gain change retunes sounds still playing, and at gain 0 no `Audio` object is created. Throttle by real time and speed (landed 150 ms at x10 or less, 600 ms to x60, 2.5 s above; horns 3 s, 12 s above x60). Horn samples are cut to 1.7 s. No music. |
| Positional sound (#125) | `modules/soundMixer.ts`, `modules/positionalSound.ts`, `modules/gantryBeacons.ts`, `modules/soundShots.ts`, `cli/sounds/synth.ts`, `assets/sounds/*.wav` | Sounds placed in the world. Each frame the kind renderers push `SoundSource`s (STS and ASC position, motion `gantrying` or `idle`; a paused sim is never gantrying) into `KindFrame.sounds`; `mixSources(camera, sources)` (pure) returns voices: gain = level x inverse distance beyond 40 m, faded to 0 at 500 m, at most 12 (loudest, ties by id); `diffVoices` gives start / stop / retune. `PositionalSound` (Web Audio, lazy, nothing created at master gain 0) loops one buffer per voice, smooths gain changes, and routes all voices through one master `GainNode` set from `useAudioStore().masterGain`; started from `useTwinScene`'s loop (one cheap mix per frame, no voices while nothing gantries). `GantryBeacons` are small amber meshes (8 per STS and 4 per ASC, at the `beaconMounts` of each model's sidecar via `stsBeaconOffsets()` / `ascBeaconOffsets()`), visible only while gantrying and on the wall-clock flash phase (800 ms). Files are generated, not sourced: `pnpm run tt:sounds` writes `assets/sounds/*.wav` from `cli/sounds/synth.ts` (pure maths, a seeded PRNG for noise; add a sound as one `SYNTHS` entry plus a `SOUND_PROFILES` entry and a `urls` entry in `positionalSound.ts`), `pnpm run tt:sounds:check` (also a Vitest suite and a CI step) regenerates in memory and fails on any byte of drift.
 The rest of the terminal (#129) uses the same path. `SOUND_PROFILES` (level, reference and maximum distance, loop or one-shot, `when` = motion states per machine kind `sts|asc|shc|truck|harbour`) is the one table: `motorWhine` (STS/ASC trolley or hoist moving, `SceneModel.isWorking`, from the trolley), `reverseBeeper` (SHC and truck on a reversing drive leg, `isReversing`), `truckEngine` (visible trucks, `idle`/`driving`, short range), and the one-shots `twistlock` (a box picked up or set down by an STS, ASC or SHC), `landingThud` (set down, not carrier to carrier) and `airBrake` (a truck's drive leg ends). One-shots are moments, not states: `SceneModel.shotsBetween(t0, t1)` reads the custody handoffs and truck leg ends in the display-time window since the last frame, and `ShotTracker` (`soundShots.ts`) keeps each as a source for 300 ms of wall clock, so it is heard at any playback speed; seeks, rewinds and a paused clock make none. `PositionalSound` plays a one-shot once (no loop) and lets it ring out; it loads every file when the context is created. `harbourAmbience` (wind, water, gulls; 8 s whole-cycle loop) is not positional: the scene renderer always pushes one `harbour` source, level 0.12, and the mixer never lets the voice cap crowd it out (it counts toward the 12). Mute and volume go through the same master gain, so they cover all of it. |
| Banner | `components/DepartureBanner.vue`, `store.banner` | 3.5 s, `pointer-events: none`, reduced-motion safe. Shown on every vessel departure regardless of volume or mute. Scenario completion uses the existing end banner (now with a soft amber glow) plus the chime. |
| Micro-copy | `modules/microcopy.ts` (`quayNote`), `i18n/messages.ts` | "Quay's quiet. Next vessel ETA 03:40" bottom-left while no vessel is at the quay or anchorage; friendlier empty states in the feed, inspector and Gantt. |
| Home card | `pnpm run tt:card` (`scripts/tt-home-card.mjs`), `assets/home-card.png`, `SimDefinition.cardImage` | Loads the TTI preset, runs to 04:30, frames the overview, hides all UI, captures the canvas at 1200x630 via `scripts/screenshot.mjs`. Re-run and commit the PNG whenever visuals change. Do not edit sim source while it runs (Vite hot reload kills the capture). |

### Per-terminal folders (`terminals/`)

A real terminal's constants and scenery live in `terminals/<id>/`, so generic modules never compare preset names. `terminals/types.ts` defines `TerminalProfile` (`id`, `label`, `presets`, `scenery`); `terminals/index.ts` is the registry (`TERMINALS`, `terminalForScenario(name)`, `terminalPresetInfo(name)`, both null for a scenario no terminal owns).

- **A preset's presentation** is `TerminalPresetInfo`: its catalogue copy (`copy`, read by `presetCopy` in `modules/scenarioPicker.ts`), `derivedBays` (the setup dialog's "bay count derived from a published capacity" note, `components/setup/ScenarioDetail.vue`) and `daylightLockDefault` (`modules/atmosphere.ts`).
- **Scenery** is a `TerminalScenery` (`kind`, `parts`, `modelParts`, `fogFarM`, optional `defaultCameraOffset`, `build(ctx)`): `buildBackdrop` adds the hinterland plane, then calls `build`; `modelParts` names the phase 2 GLBs that replace procedural parts once loaded; `defaultCameraOffset` is the opening camera's offset from the overview target (TTI: a low pose from the apron facing the water, so the Rock is on the horizon; the generic pose is (95, 70, 115)). The Quay and Overview presets stay steep and top-down by design: tilt the camera to see the Rock from them.
- **`terminals/tti-algeciras/`:** `constants.ts` (no THREE: preset names, capacity-derived layout `TTI_*`, peak-day assumptions, `NORTH_QUAY_LENGTH_M`, `ROCK`), `scenery.ts` (THREE), `index.ts` (the profile). `scenario/presets.ts` imports and re-exports the constants; the preset definitions stay there.
- **The Rock (`ROCK`, [V]):** 5.2 km north to south along +x (+x is south, the quay faces east, water towards -z), 1.2 km wide, 426 m high, centre `distanceM` 9200 m east of the quay line and `offsetSouthM` 600 m south of the quay's middle (reference map). Steep north face, summit ridge in the north half, stepped fall to Europa Point, crest toward the east, no vertical exaggeration. The procedural fallback is the profile extruded across the width; the GLB (`backdrop-rock`, 2 880 triangles, budget 4 000) adds the cross-section, rock and scrub materials. `build_backdrop_rock` in `infrastructure.py` repeats the profile: change `ROCK` and the generator together. Reference photos: `docs/reference/tti-algeciras/PHOTOS.md` lists them (the photos are git-ignored, the generator runs without them).
- **Surroundings (#123):** `SURROUNDINGS` in `constants.ts` names the five `scenery-*` assets, their placement and the budget (8 000 triangles, 5 draw calls in all). Parts `shore` (Gibraltar and La Línea at the Rock's bearing, runway and moles), `anchorage` (nine vessels in the bay, 1.5 km out and more, clear of the berth approach), `tanks` (south-west corner, beside the road), `landside` (Isla Verde road, two rail tracks, a freight train, warehouses), `town` (Algeciras on rising ground inland). Each is one mesh: a few merged boxes until its GLB loads, then the GLB geometry. The generic coastline shows none (`tests/surroundings.test.ts`). The hills behind Algeciras are the existing `hills` part.
- **To add a terminal:** a folder with `constants.ts`, `scenery.ts` and an `index.ts` exporting a `TerminalProfile`, one line in `TERMINALS`, preset names as keys of `presets`. `tests/terminals.test.ts` fails when a generic module imports a TTI preset-name constant.

Dev API: `__tt.atmosphere()` returns `{ lockDaylight, soundGain, sound: { played, recent }, positional: { voices: [{ key, gain }] }, banner, scene: { mode, daylight, shadows, masts, equipmentLights, backdrop: { kind, parts } } }`.
Positional sound proof: `tests/sound-mixer.test.ts`, `tests/positional-sound.test.ts`, `tests/sound-synth.test.ts`, `tests/gantry-beacons.test.ts`, `tests/gantry-motion.test.ts`, `tests/sound-sources.test.ts`, `tests/sound-shot-tracker.test.ts`; smoke `tests/browser/gantry-alarm.smoke.ts` (`__tt.scene().gantryBeacons` = `{ gantrying, lit }`, `sceneState().sts|ascs[id].gantrying`, `atmosphere().positional.voices`; the harbour ambience voice `harbourAmbience:harbour` is always among them).
Proof: `tests/sound-player.test.ts`, `tests/atmosphere.test.ts`, `tests/cues.test.ts`, `tests/backdrop.test.ts`; `tests/browser/terminal-twin-atmosphere.smoke.ts` (day/night, lock, draw calls day vs night, backdrop per preset, global mute honoured, default 40% gain and x600 throttle, banner click-through).
**Daylight start and readable night (V11-03).** Presets start at 08:00 local (`presets.ts`: `startAt` and `clockStart(8 * 3600)`; the setup dialog's default start, `defaultStartDate`, is Monday 08:00); fixtures keep their 06:00 start so goldens are unchanged. Night keeps an ambient floor: `ambientIntensity(daylight)` is higher at night (1.9) than by day (1.4) and the night hemisphere/moon colours are brighter, so the ground, boxes, trucks, STS cranes and ASCs stay distinguishable (checked on a screenshot of the TTI preset at 03:30: `pnpm run screenshot --path /sim/terminal-twin --eval "(async()=>{await window.__tt.load('TTI Algeciras baseline',{startDateTime:'2026-01-05T02:00:00Z'});await window.__tt.runTo(5400);window.__tt.cameraTo('B08',120)})()"`). Yard light masts (`mastSpots`, shared by the mast models and the night glow) stand only mid-gap between neighbouring blocks and beside the outermost blocks, never inside a block footprint (`BLOCK_FOOTPRINT_HALF_X_M`, the ASC rail span plus leg width): a block's centre line is where its ASCs travel. `tests/infrastructure.test.ts` asserts this for every preset and every fixture with blocks, and that each block has masts beside it.
Not done: real-GPU frame rate at night (the TT-19 budget lands separately; the smoke test compares draw calls, and night has no shadow pass); trucks have no night lights; the sun is not seasonal.
- Sound cues come from `delta.events` (capped at 200 per batch), so flat-out runs drop most of them by design; per-frame cue release is in `store.sync()`.

## Shared volume control and FPS chip (#118)

- The shared `src/components/AudioControls.vue` (a speaker button whose click mutes or unmutes at once, `aria-pressed` and labelled Mute, plus a small arrow button labelled Volume that opens a popover, teleported to `<body>`, with the volume slider; any slider movement unmutes via `moveVolumeSlider`; icon and label rules in `src/utils/audioControl.ts`) is shown by every sim page. Volume (default 0.4) and mute persist in the site storage `global` block (`volume`, `soundMuted`) via `src/stores/audio.ts` (`volume`, `masterGain`, `setVolume`). Other sims honour the shared mute; only Terminal Twin scales its playback by the volume so far. Test ids: `audio-button` (speaker), `audio-menu-button` (arrow), `audio-popover`, `audio-volume`, `audio-volume-label`.
- `SimPage.vue` renders the top-right cluster for Terminal Twin too, with a `#sim-header-slot` that `TerminalTwin.vue` teleports `components/FpsChip.vue` into (hidden when `webglFailed`, like the perf panel).
- FPS chip (`tt-fps-chip`): shows `perfStore.stats.fps` (the `FpsMeter` 1 s average); `modules/fpsChip.ts` `fpsSeverity` gives amber below 30 and red below 20 (`data-severity`). Click toggles the perf overlay, as the `p` shortcut and the Stats button do.
- Proof: `src/stores/audio.test.ts`, `tests/fps-chip.test.ts`, `tests/sound-player.test.ts`; smoke `terminal-twin-volume-fps.smoke.ts` and `terminal-twin-fps-chip.prod.smoke.ts`.
