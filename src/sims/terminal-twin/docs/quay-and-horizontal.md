# Terminal Twin: vessels, quay and horizontal transport

Engine subsystems on the waterside: vessel calls and berthing, the STS rail, and SHC transport. Guide: [terminal-twin-AGENTS.md](../terminal-twin-AGENTS.md). Terms: [GLOSSARY.md](../../../../GLOSSARY.md).

## Vessels, berthing and the STS rail (TT-09)

- **Vessel table.** `config.vessels` holds vessel *calls*: `arrivalS`, `sizeClass`, `discharge`, `load`, `transshipment`, `maxSts`, optional `sizeMix`. Berth position and cranes are NOT in the config: decision points choose them. `config.containers` no longer exists.
- **Size classes** (`scenario/vesselClasses.ts`, all [A]): LOA, beam, 40 ft bays, rows, hold and deck tiers, hatch-cover height. Frame: `berthX` = stern; bay 0 aft; row 0 quay side; tier 0 = hold floor, tiers >= `holdTiers` on deck. A cell holds one 40 ft or two 20 ft (aft `a` / fore `f` half). Slot id `V001:BB-RR-TT[a|f]`. Engine, scene model and renderer use the same `slotX/slotZ/tierBaseY`.
- **Bay plan** (`planCargo(config, seed)`, own RNG stream): discharge boxes (ISO 6346 ids, weighted lines from `cargo.lines`, sizes from `sizeMix`, `emptyShare`) spread unevenly over bays, hold/deck in proportion, stacked bottom-up; 20 ft paired fore/aft; no 20 on a 40 and no 40 on a single 20 half (R07, see `yard-and-landside.md`). Load/transshipment slots are reserved empty (`purpose`). The scene model regenerates it from config + seed, so it never crosses the worker protocol. Query: `sim.query.vesselSlots(vesselId?)`.
- **Berth flow** (`subsystems/berth.ts`): `VesselArrived` → `berthAllocation` (one pending at a time, arrival order, strictly first come first served) → `BerthAllocated` (quay stretch taken) or `VesselAtAnchorage` (asked again at every `VesselDeparted`) → `mooringS` → `VesselBerthed` → `craneSplit` → STS work → `StsWorkComplete` per crane → `VesselWorkComplete` → `unmooringS` → `VesselDeparted`. Anchorage wait = allocation − arrival (`kpis.vessels.*.anchorageWaitS`, `kpis.quay`). The engine rejects (throws, so the run fails) berths off the quay or within `berthGapM` of another vessel.
- **Crane split:** the reply lists free cranes with ascending bay ranges in rail order, covering every work bay once. The engine rejects splits that would make cranes pass (`validateSplit`). No cranes → the vessel waits berthed and is asked about again whenever a crane is freed. Both strategies pick up to `maxSts` eligible free cranes nearest the vessel (eligible = no busy crane would have to pass them), then split the bays: `balanced-moves` (min-max moves, dynamic programming) or `equal-bays`.
- **Rail** (`subsystems/rail.ts`): each STS has a reservation `[railLo, railHi]` covering its current gantry motion; neighbours stay `quay.stsMinSpacingM` (27 m) apart. A move that needs the rail waits (`StsWaitingForRail`, status `waiting-for-rail`, `kpis.sts.*.railWaitS`), and `wakeRail` retries after every rail change. A free idle crane in the way is asked to step aside (`StsRepositionStarted/Completed`). Reservations shrink at `StsPicked`. The `sts.rail-order` invariant checks order, spacing and position-within-reservation after every event; `berth.no-overlap` checks vessels.
- **STS cycle:** the gantry move is part of `StsMoveStarted`'s plan (hoist up, gantry, trolley, hoist down). Work order per crane: bay ascending, deck before hold, top tier first, row ascending, aft before fore. **Twin-20** (`quay.twinLift`): the aft and fore halves of one cell are picked in one `StsPicked` (`payload.twin`); each gets its own ground-position decision, and they are set down one after the other (two `StsGrounded`, `payload.x` = set-down X) before the next cycle [A: sequential release]. KPIs: `moves` (boxes), `cycles`, `twinLifts`.
- **End:** with no end condition configured, the run ends when every vessel has departed.
- **Browser:** vessel entity deltas carry `berthX`. The scene places hulls (TT-27 GLBs per class behind a procedural placeholder, in the livery of the vessel's line; see [Vessel hulls](equipment-models.md#vessel-hulls-tt-27)) at the berth or in an anchorage row offshore. Twin boxes on the spreader use `CustodyChange.dx`. Run-to compaction (`compactMotion`) keeps each entity's latest motion plan whole (an SHC trip is one multi-segment plan) plus the latest earlier segment of every axis that plan does not move. Setup dialog: quay length, STS count (`spreadSts` spreads them evenly), vessel table and generator → `ScenarioChoice.overrides` → `applyOverrides`; `__tt.load(name, { overrides })` does the same.

- Berth allocation is strictly first come, first served: a vessel that never fits (LOA > quay) blocks the queue for good (the setup dialog warns).
- A free crane steps aside only if its other neighbour leaves room (chains of free cranes move one after another). A busy crane is never pushed, so a waiting crane may idle until its neighbour finishes.

## Horizontal transport: SHCs (TT-05)

- **Config** (all optional, so older fixtures are unchanged): `shcs: [{id}]`, `kinematics.shc` (`DEFAULT_SHC_KINEMATICS` [A]), `yard.blocks: [{id, x, wtpPads}]`, `apron` (lane geometry, `DEFAULT_APRON_LAYOUT`), `driverVariabilityPct`, `subsystems: {shc, asc}`. Builder: `.shcs(n, kin?)`, `.block(id, {x, wtpPads})`, `.driverVariability(pct)`, `.subsystems({...})`; `withShcFleet(config, n, kin?)` (setup dialog).
- **Lane graph** (`engine/laneGraph.ts`, pure, cached per config object): one continuous one-way (+X) STS lane per ground-position lane along the whole quay; **stations** every `stationSpacingM` (25 m) with a down spine (westbound apron → lanes, nodes `D<k>:<lane>`) and, 5 m further, an up spine (lanes → westbound apron, `U<k>:<lane>`); a westbound/eastbound apron loop (`AW@x`, `AE@x`, crossovers at every apron X); WTP pads as spurs off the eastbound lane (`AE → C:<padId> (clear position) → P:<padId>` and back); one parking spur per SHC (`S:<shcId>`) west of everything. Every edge is along X or Z. `laneAccess(graph, lane, x)` gives the lane walk for a box at x; `laneZonesAt` the zones a set-down covers. Pads: `<blockId>-WTP<n>`, centred on the block, boxes along Z.
- **Conflict zones and reservations** (`engine/reservations.ts`): zones are intersections (apron and lane/spine nodes), each STS lane section between two lane nodes (`L<lane>@<x>`), and each pad with its spur. A trip reserves `[t(enter − clearance), t(leave + clearance))` for every zone visit before it starts; if any window overlaps, **the whole trip departs later** (`earliestStart`). Vehicles therefore wait only where they rest (parking spot, pad clear position), which are not zones. With SHCs, the STS also reserves the lane sections under the box from the start of the carry until the box is down, and delays the carry if an SHC is still there. Windows are half-open; zero-length (instant) windows are not stored.
- **Jobs and dispatch:** `StsGrounded` releases a job (`J<n>`) into the pool. `maybeDispatch` asks one free SHC (available first, then parked, by id) per open job/free pad not already being asked about. The `shcDispatch` decision point replies `{jobId}` (null → the SHC parks); for a discharge job the SHC then asks `wtpPadSelection` (`{wtpPadId}`; null → job given back, SHC parks). Strategies: `shcDispatch` `oldest-job` (default; FIFO) and `nearest-job` (shortest route); `wtpPadSelection` `first-free` (default), `nearest-box`, `last-free`. The engine **trusts** the reply; invariants catch a double claim or a double-occupied pad.
- **Trip:** the whole job is planned at once (straight runs; each turn is taken at a capped corner speed `cornerSpeedCap` from the turn angle and an assumed radius, so the x and z segments share `v1`/`v0` there, while reversals, locks and pads are rest points; lock/lift/lower/unlock at the box and pad) and installed as `ShcState.motion` + `ShcState.plan`. Phase events chain (`ShcJobAssigned → ShcRoutingEmpty → ShcPositioningAtPickup → ShcLocking → ShcPicked → ShcRoutingLoaded → ShcPositioningAtDropoff → ShcLowering → ShcUnlocking → ShcDroppedAtWtp → ShcCleared`), each carrying the `segments` that led up to it. "Positioning" = the final straight run into the box/pad. Custody: GP → SHC at `ShcPicked`, SHC → pad at `ShcDroppedAtWtp`. Idle SHCs: `ShcRoutingToParking → ShcParked`.
- **Waiting:** a `null` ground-position reply → `StsWaitingForGroundPosition` (status `waiting-for-ground-position`); when an SHC picks a box off that crane's lane, `StsGroundPositionWaitEnded {waitedS}` fires and the STS asks again; with no freed position it asks again after `layout.stsGroundRetryS` (default 30 s, 0 = off; `StsGroundPositionWaitBackoff` timer). KPI `horizontal.stsGroundPositionWaitS`.
- **Quay, berth and yard modes** (V11-10; `config.subsystems.quay|berth|yard`, same override rules, resolved into `SimState.subsystems`): quay `instant` zeroes every STS motion (`seg.t1 = seg.t0`), lock and unlock, and the gantry reposition, same events (an instant crane can outrun its feeders, so extra `Sts*Waiting*` events may appear); quay `off` raises no STS work (vessels berth, `VesselWorkComplete` at once, the load flow is inactive). Berth `instant` zeroes mooring and unmooring; berth `off` skips the `berthAllocation` decision (first-fit leftmost stretch in arrival order, anchorage if none fits) and also moors instantly. Yard `instant` runs the ASC instant unless `asc` is set explicitly; yard `off` forces ASC and landside off (boxes stay on the pads). `validateSubsystemModes` (also in `validateScenario` and `createSimulation`, including `options.subsystems`) rejects instant quay without STS cranes, instant yard without blocks, and yard `off` with an explicit running ASC or landside. CLI: `--subsystem quay=instant` (repeatable; exit 2 on a bad or impossible value). Setup dialog: "Subsystem modes" fieldset (`tt-mode-<quay|berth|yard>-<real|instant|off>`) via `ScenarioOverrides.subsystems`. Tests: `tests/subsystem-modes.test.ts`.
- **Subsystem modes** (`SimulationOptions.subsystems` overrides `config.subsystems`; resolved into `SimState.subsystems`): SHC `real` (default with SHCs + blocks) / `instant` (same events, zero durations) / `off` (no jobs; boxes stay on ground positions). ASC `real` (default with SHCs + blocks) / `instant` (same events and the same `yardAllocation` decision, zero durations; the ASC still waits for `ShcCleared`) / `off` (no ASC: pads fill up). Fixture `shc-1sts-2shc-1wtp` pins ASC `instant` so it tests SHC transport on its own.
- **KPIs:** `kpiReport().horizontal` (only with SHCs): `boxesToWtp`, per SHC `jobs`, `emptyDistanceM`, `loadedDistanceM`, `reservationWaitS`, and `stsGroundPositionWaitS`. The CLI prints a `Horizontal:` block.
- **Invariants added:** `reservation.no-overlap`, `claim.single-holder`. Double occupancy of a ground position or pad surfaces as `custody.single-owner` with "… is double-occupied: X was set down on it" (a place holds one `containerId`).
- **Browser:** the worker diffs `ShcState.motion`/`status` like the STS and sends new reservations (`Delta.reservations`). `SceneModel.shcPose(id,t)` → `{x, z, lift, heading, yaw, steerRad, odometerM, travelling}`; `containerPose` adds a yaw (boxes on pads/SHCs heading Z lie along Z; a carried box takes the SHC's yaw). Overlays: `store.overlays` / `OverlayToggles.vue` (catalogue keys `overlays.*`) / `__tt.overlays()`; the O shortcut (`store.overlaysVisible`) is the master switch over them. The setup dialog edits SHC speeds in display units (km/h or mi/h, m/s² or ft/s²) and stores SI.

- Fixtures without SHCs give each STS enough ground positions for all its boxes (tracer 10, others 6–30) because nothing clears them; SHC fixtures use a realistic 3.
- `shc-1sts-2shc-1wtp` (3 ground positions, 2 SHCs, block B01 with 4 pads west of the crane) ends at `simDurationS 1800`, after every box is in the yard.
- SHC trips are planned whole at dispatch; a later conflict never re-plans a trip, it only delays the next trip's departure. A vehicle waiting at a pad clear position holds no reservation, so another SHC approaching that same pad can pass through it visually (rare; dispatch is instant).
- STS lanes are continuous along the quay (cranes move, TT-09): an SHC enters a lane at the down spine before the box (stations every `stationSpacingM`, 25 m) and leaves at the up spine after it. The STS reserves the lane sections it sets a box down in, so traffic in that lane and the set-down never overlap.
- With SHCs, the STS lanes must stay clear of the apron: `validateLaneLayout` rejects ground-position counts whose last lane reaches the westbound apron lane (≥ 11 lanes with the default layout).
- Lane-node count grows with quay length x ground-position lanes (a 2 km quay with 3 lanes is about 1,000 nodes): fine with the path caches, but watch it at TTI scale.

## Hatch covers (TT-R09, ENGINE_VERSION 0.15.0)

STS cranes lift the hatch panels off a bay when its hold has work and put them back afterwards. Code: pure part `engine/hatch.ts` (settings, laydown geometry, `hatchLaydownProblems`, `createHatchPanels`), reactors `engine/subsystems/hatch.ts`, sequencing in `engine/subsystems/workPackages.ts`. Terms: [GLOSSARY.md](../../../../GLOSSARY.md) (hatch panel, hatch move, hatch laydown, lashing release).

- **Config.** Per vessel class (`VESSEL_CLASSES[...].hatch`, all [A]): `panels` across the beam (feeder 2, feedermax 2, panamax 2, neo-panamax 3, ULCV 4), `panelLengthM` 13.5, `panelWeightT` (12 to 32), `lashingReleaseS` 300, `lashingSecureS` 180, `cycleS` 240 and `laydownStackLimit` 3. Panel width follows from the rows it covers (`hatchPanelRows`, row pitch less a 0.3 m gap, at most 15 m). The counts are not the spec's example (1, 2, 3, 3): a panel has to fit the laydown bay (see below), which caps it at about 15 m across. `ScenarioConfig.hatch` (builder `.hatch({...})`) overrides the timings and the stack limit for every class; `hatch: { enabled: false }` turns the hatch covers off (no panels, no hatch moves, the old discharge-then-load work order). `VesselConfig.deckOnly` stows the discharge boxes on deck only (used by `hatch-deck-only-no-open`).
- **State.** `state.hatchPanels[id]` (`HatchPanelState`: id `V001:H04-1`, rows covered, size, weight, `home` and `pos` as the top-face centre, `status`, `opens`, `deckBoxes`, lashing and lift times, `siteId`/`level` in the laydown, `placedOn`), `state.hatchLaydown[siteId]` (stack, bottom first), `VesselState.hatchPanelIds`, `StsState.hatchJob/carryingPanel/hatchWaitPanel`. Panels exist for every bay that has a slot, are created secured at the start and positioned when the vessel is given its berth. They are not containers: no custody, no yard slot, no move count (`tests/hatch.test.ts` checks it).
- **Work order (hatch on).** `createPackages` orders a crane's packages bay by bay: deck discharge, `hatch-remove` for each panel that has hold work under it (hold discharge, or a hold load slot), hold discharge, hold load, `hatch-replace` (last panel removed first, so the top of a laydown stack goes back first), deck load. A bay without hold work gets no hatch package. `loadPrep.ts` stages a load box once the crane has finished the discharge packages that come before its package (the old rule, "all discharge first", is the case with hatch off). Hatch packages have `kind` `hatch-remove`/`hatch-replace`, section `deck`, no boxes (`packageMoves` 0) and `hatchPanelId`. The `workPackageRelease` contract is now version 2 (the kinds).
- **Events.** `HatchLashingReleased` (panel `unsecured`) comes `lashingReleaseS` after the last deck box over the panel is picked (`deckBoxChanged` in the `StsPicked` reactor; at crane assignment for a panel with no deck box). The crane starts a hatch package with `StsHatchStarted` (raised again after a rail wait or a lashing wait; `StsWaitingForHatch` when it idles): rail reserved for the whole move (`reserveRail(..., alsoX)`, so the gantry to the laydown is covered), gantry/trolley/hoist to the panel, lock → `HatchLifted` (`from` `hatch` or `laydown`) → carry → `HatchSetInLaydown` (removal) or `HatchReplaced` (replacement) → `HatchSecured` after `lashingSecureS`. Each is caused by the one before. Panels and the crane are the `equipment` subjects.
- **Cycle time.** A hatch move (start to set down) is the planned crane motion plus handling time so it lasts `cycleS` (default 240 s; the hoist back up to the safe height comes after, so a move measures a little more). The pad is split over the lock and the unlock. Quay mode `instant` zeroes it and the lashing delays too.
- **Waiting.** The crane idles for a lashing release before a removal, for securing before a deck load onto a replaced hatch (`hatchBlocker` in `prepareNextPackage`), and for the last securing before `StsWorkComplete` (the vessel does not leave with an unsecured panel). KPI `hatch.waitS` sums the idle time.
- **Laydown.** Panels go to the nearest laydown bay with room, one stack of one hatch per bay (`LD@<x>`, X = 25 k with the default station spacing: the middle of the gap between an SHC up spine and the next down spine). Z is landside of the last ground lane plus SHC half width plus 0.4 m, so it is between the lanes and the landside STS rail (Z 33.48): about Z 16.9 to 32 with 3 lanes. `hatchLaydownProblems(config)` checks every laydown bay at the widest panel against ground lanes, rails and (with SHCs) lane-graph nodes with vehicle half width, edges and conflict zones; `createInitialState` throws when it fails, which for SHC scenarios means more than 3 ground positions per STS (turn hatch covers off for those). No-SHC scenarios with many ground lanes put the laydown landside of the rail. The laydown is by bay, not per STS: bays of a hatch never mix, and with bay-by-bay sequencing at most one hatch per crane is open at a time.
- **Invariants** (each has a tampered-snapshot test in `tests/hatch.test.ts`): `hatch.no-removal-with-boxes-on-top`, `hatch.no-lift-before-lashing-release`, `hatch.no-hold-access-through-closed-hatch` (spreader below the hatch plane over a closed panel, from the planned end positions of the motion), `hatch.no-deck-load-on-missing-hatch`, `hatch.replace-own-hatch`, `hatch.laydown-stack-limit`, `hatch.no-departure-open`. Hatch events name their panel in `subjects.equipment`, which is what the scoped checks look at.
- **KPIs.** `kpiReport().hatch` (only once a hatch move started): `moves`, `removes`, `replaces`, `stsTimeS`, `waitS`, per STS `{moves, timeS, waitS}`. Hatch moves are not in `sts.*.moves` or gross moves per hour; `lastMoveEndS` includes them. The CLI prints a `Hatch covers:` block.
- **Fixtures.** `hatch-cover-cycle` (28 empties fill bay 0's hold and then its deck, so bay 0 has deck discharge, hold discharge, hold load and deck load) and `hatch-deck-only-no-open` (deck-only discharge: no hatch moves). The other fixtures set `hatch.enabled: false`, so their tests and goldens are about their own subject; the presets run with hatch covers on.
- **Latent races the hatch timings exposed (fixed here).** (1) `berth.ts`: an empty `craneSplit` reply (a free crane that cannot take the vessel) used to re-ask at once, looping at one instant; the vessel now stays at the head of the queue until a crane is freed or a vessel berths. (2) `shc.ts`: two SHCs asking at the same sim time were built requests from the same job and pad lists, so a built-in strategy could hand both the same job or pad (`claim.single-holder`); a stale built-in reply now asks again. A custom handler is still trusted, as `tests/shc-transport.test.ts` relies on.
- **Not built (3D, #92).** The scene model and renderer do not draw panels yet: the GLB's `hatch_covers` stay static.

## SHC queue areas and chained dispatch (TT-R12, ENGINE_VERSION 0.20.0)

Code: lane graph `engine/laneGraph.ts` (`queueAreas`, `queueAreaOf`, node kind `queue`), SHC subsystem `engine/subsystems/shc.ts` (`goQueue`, `assignQueuedJob`, `resumeFromQueue`, `serveQueues`, `goIdle`, `isChained`, `workRemains`). Terms: [GLOSSARY.md](../../../../GLOSSARY.md) (queue area, chained dispatch).

- **Config.** `ScenarioConfig.queueAreas: { stsCapacity?, blockCapacity? }` (builder `.queueAreas({...})`; absent = no queue areas and the old behaviour, so older fixtures keep their graph and event logs). `ApronLayout.queueZ` (58) and `queuePitchM` (8) place the spots. One area per STS (`QS:<stsId>`, near the crane's start `gantryX`) and one per block (`QB:<blockId>`, east of its pads); spots are rest nodes on spurs off the eastbound apron lane, nudged along X to stay clear of every pad column. Spots are not conflict zones (like parking). The TTI presets set 3 and 3 [unverified, assumed].
- **State.** `state.queueClaims` maps spot node id to the holding SHC (exclusive; held from the assignment that targets the spot until the SHC leaves it). `ShcStatus` gains `queuing-for-pad` (loaded, resting at a block spot) and `queuing-for-work` (empty, resting at any spot); operational states map to `queuing-to-deliver` / `queuing-to-collect` (a `waiting-for-pad` SHC that carries a box is also `queuing-to-deliver`).
- **Waiting for a pad (loaded).** A discharge job is normally dispatched only with a free pad. With block queue spots, dispatch also starts when no pad is free: the SHC fetches the box (freeing the ground position) and drives it to the nearest block queue area with room (`ShcJobAssigned` with `wtpPadId` ''; trip ends in `ShcQueued`, `loaded: true`). Whenever a pad frees (`maybeDispatch` runs `serveQueues`) a queued SHC asks `wtpPadSelection` again, one per free pad; a `null` reply keeps it waiting. On a pad reply `resumeFromQueue` plans the loaded drive from the spot (`ShcQueueDeparted`, then the usual `ShcRoutingLoaded` ... `ShcDroppedAtWtp` -> `ShcCleared`). Pad claims stay exclusive, so a box is never delivered into a full pad.
- **`chained-nearest`** (`shcDispatch` strategy; engine behaviour keyed on `config.decisions.points.shcDispatch.strategy`, see `isChained`): the handler is nearest-job; after `ShcCleared`, or a `null` reply, the SHC goes to the nearest free queue spot (STS or block area) while `workRemains` (an open job, or a vessel mooring or berthed) and waits there (`ShcQueued`, `loaded: false`, status `queuing-for-work`). `maybeDispatch` also asks queued-for-work SHCs (after `available`, before `parked`). It parks (`goPark`) when no work remains (`VesselWorkComplete` reactor), or when every spot is taken. `oldest-job` and `nearest-job` keep returning idle SHCs to their parking spots, so strategies compare with `tt:run --strategy` and `tt:diff` on saved event logs.
- **Events.** `ShcQueued {nodeId, areaId, jobId, loaded}` (arrival at a spot) and `ShcQueueDeparted {jobId, wtpPadId, departAt}` (a loaded SHC left its spot for a pad). A queue drive of an empty SHC reuses `ShcRoutingToParking` (it is the drive that ends in `ShcQueued`).
- **KPIs.** Per SHC `parkingReturns` (drives to the parking spot) and `queueArrivals` in `kpiReport().horizontal.shcs`; the CLI prints both per SHC and the total on the `Horizontal:` line. Time at a spot lands in the existing states (`queuing-to-deliver`, `queuing-to-collect`).
- **Invariant.** `shc.waiting-positions`: a `parked` SHC is on a parking spot, a resting `queuing-*` SHC is on a queue spot it holds, no SHC stands on a queue spot held by another, and every claim names an SHC at that spot. A waiting SHC is therefore never on a ground position, WTP pad or lane node. Negative tests (tampered snapshots) in `tests/shc-queue.test.ts`.
- **Fixture.** `shc-queue-chained` (2 STS, 24 boxes, 4 SHCs, 1 pad, real ASC, queue areas of 2, `chained-nearest`): about 0 parking returns versus 19 with `oldest-job`. Prove with `pnpm run tt:run --fixture shc-queue-chained --strategy shcDispatch=oldest-job` against the default.
- **3D.** `sceneRenderer.ts` paints parking spots (grey) and queue spots (blue near STS, orange near blocks) as ground bays beside the pads; always visible, not an overlay.
- **Limits.** The empty-SHC STS queue is a waiting place for the next job; sending SHCs ahead of a predicted box is the `predispatch` strategy below (TT-R13). Queue areas are per STS home position (the crane gantry moves, the spot does not). Without `chained-nearest` the STS areas are unused. Load-job drop-offs never wait (their ground position is claimed in advance).

## SHC pre-dispatch on predicted ready time (TT-R13, ENGINE_VERSION 0.21.0)

Code: `engine/predictions.ts` (`predictedReady`), `predictedGroundings` in `subsystems/quay.ts`, `predictedPadReady` in `subsystems/asc.ts`, `maybePredispatch` / `predictionDeficits` / `isPredispatch` in `subsystems/shc.ts`. Terms: [GLOSSARY.md](../../../../GLOSSARY.md) (predicted ready time, pre-dispatch).

- **Predictions.** `sim.predictedReady()` lists `{source: 'sts'|'asc', ownerId, readyAt, containerId, exact}` soonest first. Quay: a crane's planned carry is published at its scheduled `StsGrounded` time (`StsDrop.groundAt`, set in `planDrop`; `exact: true`); the next two boxes of its work packages are estimated as (crane free time + `stsNominalCycle` per box + the vessel class's hatch `cycleS` for each hatch package in front), `exact: false`. Discharge only. ASC: an ASC retrieval whose cycle is planned is published at its planned `AscDroppedAtWtp` time (`exact: true`; the box then becomes a load job). Pure reads: nothing here changes engine behaviour by itself.
- **Strategy `predispatch`** (`shcDispatch`; chained-nearest handler, engine behaviour keyed on the strategy name like `chained-nearest`, so `isChained` is also true). `maybePredispatch` runs after `maybeDispatch` and on `DecisionResolved` of `stsGroundPosition`, `StsMoveStarted`, `StsHatchStarted` and `AscJobAssigned`. A prediction is covered when an idle SHC waits at (or drives to) the queue area of its STS (`QS:<sts>`) or block (`QB:<block>`). For each uncovered prediction the nearest spare SHC (parked, or waiting at an area with more idle SHCs than predictions) is sent to a free spot of that area when `readyAt - now <= travel time + queueAreas.predispatchMarginS` (default `DEFAULT_PREDISPATCH_MARGIN_S` 15 s; travel time from the empty drive profile and the lane-graph route). After a delivery `goIdle` heads for the earliest uncovered prediction's area instead of the nearest one. The drive reuses `ShcRoutingToParking`, whose payload gets `predicted: {areaId, readyAt, source}` (only under this strategy, so other event logs are unchanged).
- **No early collection.** The SHC claims a queue spot, never a job: the job exists only after `StsGrounded` / `AscDroppedAtWtp`, so `ShcLocking` can never find the box missing, STS and ASC set boxes down whenever a ground position or pad is free (they never wait for an SHC), and claims stay exclusive. Tests in `tests/shc-predispatch.test.ts` check pick and assignment times against the grounding events.
- **Fixture.** `shc-prepositioning` (2 STS with one ground position each, 4 SHCs, 3 pads, queue areas 3/3, margin 15 s): total STS ground-position wait drops against the same scenario with `chained-nearest` (about 80 s to 0). Prove with `pnpm run tt:run --fixture shc-prepositioning` and again with `--strategy shcDispatch=chained-nearest`.
- **Limits.** Upcoming-box estimates ignore rail waits, SHC shortage and move variation. Predictions are re-evaluated on events, not on a timer, so a long quiet period delays a send. The TTI presets still use `chained-nearest`. No new KPI: count `ShcRoutingToParking` events with `predicted`.

## Paired discharge/load dispatch (TT-R14, ENGINE_VERSION 0.23.0)

Code: strategy `paired-dual-cycle` in `engine/decisions/strategies.ts` (`PAIRING_RADIUS_M`), `isPaired` and the `ShcCleared` / `requestDispatch` changes in `subsystems/shc.ts`. Terms: [GLOSSARY.md](../../../../GLOSSARY.md) (paired dispatch).

- **Strategy `paired-dual-cycle`** (`shcDispatch`; selectable per scenario via `.decisions({ points: { shcDispatch: { strategy } } })` and from the CLI with `--strategy shcDispatch=paired-dual-cycle`). Engine behaviour is chained dispatch (`isChained` is true: queue areas, no parking return while work remains, same waiting rules as `chained-nearest`). The handler adds the pairing: after an SHC set a box down on a WTP pad (a discharge delivery) it prefers the nearest open load pickup, and after it set a box down on an STS ground position (a load delivery) it prefers the nearest open discharge pickup, provided that job is within `PAIRING_RADIUS_M` (150 m of route, assumed) of the SHC; otherwise, with no opposite job open or none in range, or no history yet, it takes the nearest job like `chained-nearest`. The SHC therefore drives loaded more often and returns empty a shorter distance between a pad and the quay.
- **Request field.** `ShcDispatchRequest.lastJobKind` (`'discharge' | 'load'`) is the kind of the job the SHC delivered last (`ShcState.lastJobKind`, set on `ShcCleared`). It is present only under this strategy, so other event logs, snapshots and goldens are unchanged. A custom handler can use it too.
- **Reassignment.** Any SHC may take any job: there is no fixed SHC-to-STS or SHC-to-block assignment, so a paired SHC serves several cranes and blocks over a run.
- **No new claims.** Pairing only changes which open job the handler names. Pad and queue claims, the "no set-down into a full buffer" rule and the `shc.waiting-positions` invariant are untouched; `tests/shc-paired-dispatch.test.ts` checks that runs end with 0 violations and no stale claims.
- **Fixture.** `shc-paired-dual-cycle` (one feeder discharging at STS01 and one loading at STS02 at the same time, 3 SHCs, 2 pads 150 m along the quay, queue areas of 2): SHC empty travel about 7364 m versus 7665 m with `chained-nearest` for the same 16 boxes moved to pads and the same loaded work. Prove with `pnpm run tt:run --fixture shc-paired-dual-cycle` and again with `--strategy shcDispatch=chained-nearest` (compare the `SHC empty travel` and `empty travel ratio` lines).
- **Limits.** The gain is small where `nearest-job` already pairs by geometry (a block next to the quay start, widely spaced cranes); it shows when the nearest job is of the same kind as the one just delivered (the fixture's layout). Discharge and load jobs are open together only when two vessels, or hatch-free and hatch-covered bays, work at once: a single vessel discharges first and loads after, so pairing has nothing to pair there. The strategy does not wait for a load box that is not yet on a pad (no hold for a predicted load) and does not combine with `predispatch`.
