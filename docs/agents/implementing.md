# Implementing a spec with subagents

For the orchestrator running `/implement-spec`, and the brief each **implementer** subagent receives. Terminal Twin (spec #24, tickets #25–#52) was built this way.

## Orchestrator

`handover.md` is a per-run tracking file at the repo root, not a permanent doc: create it when a run may span sessions (a ticket table with a Claimed by column, the next steps, open points), keep it current after every merge, and delete it before the PR merges to `main`. Terminal Twin's last version is in git history (`git log --diff-filter=D -- handover.md`).

0. **Push the branch.** Before spawning anything, `git push -u origin <integration-branch>` even when it equals `main`; without a remote branch the stop hook counts every commit as unpushed.
1. **Resume first.** Another session may have pushed. `git fetch`, read `git log HEAD..origin/<integration-branch>` and the `handover.md` diff, pull, `pnpm install`, then work from the merged state. Claim a ticket in `handover.md` (commit and push) before starting it.
2. **Frontier.** Read the spec once (it can be 30 KB) into a scratchpad file `spec-<n>.md`. The ticket bodies are the scratchpad files described in `docs/agents/issue-tracker.md`; re-read those files, not the issue, after a compaction. Name their paths in the brief as absolute paths (a scratchpad path is absolute, never relative to a worktree): implementers have no GitHub access. Check that every file a ticket's brief names under `docs/reference/` exists (see `docs/reference/README.md`); if not, ask the user to upload it before spawning. The photos are committed, so worktrees contain them. The spec's last ticket, "Run the browser smoke suite and fix regressions" (blocked by every other ticket), starts only when everything else is merged and no other test run is going; per-ticket merges skip smoke. Start one implementer per unblocked ticket, in its own worktree (`isolation: worktree`) on `tt/<issue>-<slug>`, in the background. Keep to at most two implementers plus one merge running at once: the container has 4 cores, each browser test is CPU-bound on software WebGL, and a third test run slows all of them past their timeouts. Each worktree also carries its own `node_modules`, builds and browser artefacts on a shared disk.
3. **Merge.** When one reports, run `scripts/merge-ticket.sh --push tt/<N>-<slug>` (in the background; it logs to `.merge-ticket.log`, whose last line is `EXIT <code>` when done): it merges the branch, stops on a conflict, runs `pnpm run verify` (which also fails on leftover conflict markers), and does not run the browser smoke suite: that runs once, in the spec's final ticket ("Run the browser smoke suite and fix regressions", blocked by every other ticket), which finds regressions by running the whole suite on a quiet machine and bisecting over the ticket merge commits. `--smoke` (changed-path specs, `scripts/smoke-specs-for.sh`, map in `scripts/smoke-map.txt`) and `--smoke-all` stay available on request. Add a line to the map when a ticket adds a spec or a new area. Keep both sides of additive conflicts (decision-point registries, fixture lists, guide sections), then `git add`, commit and re-run verify. After a green merge the script itself sets the ticket's `handover.md` row to `merged in branch (<merge sha>)`, clears its Claimed by cell, and commits that change alone (no other line changes); `--push` pushes it with the merge, otherwise run `git push` yourself. A missing row is a warning: set it by hand. Then, by hand (scripts have no GitHub access), label the ticket's issue `merged-in-branch` (keep its other labels; the issue stays open until the PR merges and closes it, so the label is the progress view in the issue list), and free the disk with `scripts/remove-worktree.sh <agent-id>`. That script unlocks and removes a locked worktree whose agent has finished; it refuses, with the pid and command, a worktree a live process has as its working directory, and one with uncommitted work.
4. **Warn.** A ticket that changes the engine contract (decision-point shapes, event payloads, `ENGINE_VERSION`) gets a `SendMessage` to the agents still running so they merge the tip early. Each such ticket takes the next minor above the tip's `ENGINE_VERSION` when it merges the tip before reporting; when two branches collide on `ENGINE_VERSION` alone, `scripts/merge-ticket.sh` writes the higher with its minor +1 and commits the merge itself (any other conflict still stops). It then runs `scripts/check-engine-version.sh`, which fails when a merge lowers the version.
5. **Rate limits** end agents mid-ticket with work uncommitted. Resume the same agent with `SendMessage` after the reset rather than starting a new one; its worktree keeps the work.
6. **Finish.** After the smoke ticket is merged, `/code-review` the integration branch, fix the findings in one implementer, and make the PR body say `Closes #<n>` for the spec and every ticket the branch finishes (GitHub closes only those on merge), mark the draft PR ready (a spec that asks for one PR per slice while the session may push only the integration branch gets one PR; tell the user), remove the remaining worktrees with `scripts/remove-worktree.sh` (a refused one is still in use: stop its process or commit its work first), delete `handover.md`. After the PR merges, start the next phase on the same branch name with `git merge --ff-only origin/main` (the branch is an ancestor of the merge commit); a force-push is blocked in cloud sessions.

## Fast mode

When the owner asks for it (to save wall-clock time on a long spec), a brief that says **fast mode** replaces the full checks:

- **Implementer:** `pnpm run lint`, `pnpm run build`, `pnpm run test:related <integration-branch>` and a screenshot for UI tickets. No `pnpm run verify`, full unit suite or smoke spec; smoke specs it writes or edits wait for the final smoke ticket. Engine tickets still record a KPI comparison and leave goldens alone.
- **Orchestrator:** merge with plain `git merge`, then run `pnpm run test:related` with no argument on the merged tree before pushing. On a merge commit the base is its first parent (the previous tip), and the first output line names it, so the run tests what the merge brought in. Zero changed files exits 1 (`--allow-empty` opts out). A red test there belongs to that ticket: send it back, or fix it before the next merge, so failures never pile up for the end. Golden tests stay red on purpose until the final ticket regenerates them once.
- **Final smoke ticket:** starts with `pnpm run verify` and the single golden regeneration, then the smoke suite as usual.
- **Smoke is the long pole** (phase 1: 2 h 12 min; the suite runs serially, `workers: 1`). Run the whole suite once with `--reporter=line` in the background via `scripts/bg.sh run --heavy <log> ...`; re-run only the failures with `--last-failed` (a spec that fails there is run alone up to three times, a spec that passes is load-sensitive). Fix failing specs in a batch, then re-run the suite's failures once more, not the suite.

## Implementer brief

- **Base (step one):** run `scripts/worktree-base.sh <integration-branch>` in your worktree before anything else. It puts the worktree on the integration branch tip and prints one line (`worktree-base: ...`). It refuses with exit 1, changing nothing, on uncommitted or untracked changes, when the base is neither a local nor an origin branch, or when your HEAD holds commits the tip lacks. On a refusal, report its line and stop. Then, if the worktree is not on `tt/<N>-<slug>` yet, `git checkout -b tt/<N>-<slug>`.
- **Read first:** the spec and ticket files named in your brief by absolute path (if any given path does not exist, stop with a one-line reason; do not guess another), the sim guide and `GLOSSARY.md`, and the notes the earlier tickets left (`handover.md`, the sim guide's topic docs).
- **Build test-first** with the `tdd` skill, through the public seams the spec names (engine API, decision-point handlers, `window.__tt`, asset outputs). Meet every acceptance criterion; say exactly why if one is impossible here.
- **Prove it:** `pnpm run lint`, `pnpm run build` and `pnpm run test:related <integration-branch>` (every unit test that imports a file you changed, committed or not; keep the explicit base even after merging the tip, since with no argument a merge commit tests only what the tip brought in), then once `pnpm run verify` in the background. UI tickets also a screenshot you look at, and the smoke specs for your diff (`scripts/smoke-specs-for.sh <integration-branch> HEAD`; run those with `pnpm run test:smoke --project=dev <names>`), plus the specs for any shared control you moved (the setup dialog, the scenario picker; `tests/browser/scenarioPicker.ts`). An engine ticket whose acceptance names a scale above 0.1 proves each fix at scale 0.1 first and runs the larger scale once, only when 0.1 is green. Run only the smoke specs for your diff. Do not run the whole smoke suite, `@load` specs, or `golden-update` and `invariants-incremental` more than once: the spec's final smoke ticket runs the rest.
- **Screenshot (UI tickets):** commit one compressed PNG of the ticket's after state, from the `pnpm run screenshot` output in `.screenshots/` (gitignored), under `docs/prototypes/`, in a folder named for the issue number (issue 170 gives folder `170`). Keep it small: compress it and crop or scale it to the view that shows the change. One file per ticket.
- **Commit early**, as soon as verify passes, and again at the end. An implementer that stops (rate limit, disk) with uncommitted work costs a full re-triage. Do not push and do not touch GitHub; the orchestrator does that.
- **Before reporting:** merge the current integration tip, re-run `pnpm run verify`, update the sim guide and `GLOSSARY.md` for what you added.
- **Done means checked:** for every acceptance criterion, name the evidence you looked at (a test, a log line, what the screenshot shows). A screenshot that does not show the criterion (the far end of a road, a distant label) is not evidence: re-frame it or report the criterion unmet. Stop only with a committed deliverable and the report below; diagnostics still running are not a result.
- **Report** (at most 12 lines): branch, tip SHA, worktree path, verify result, unmet criteria and follow-ups. Before it, stop every process you started (`sleep` loops, dev servers, watchers); the orchestrator cannot remove a worktree that still has one.

## Time box

No single stretch of agent work or wait runs past about 10 minutes without a checkpoint:

- **Waits:** `scripts/bg.sh wait` returns after 600 s by default (exit 124 means still running); the agent reads `scripts/bg.sh tail <log>`, then waits again. A job that needs hours (the smoke suite, a peak-day run) keeps running in the background; only the waiting is chunked.
- **Slices:** the orchestrator sizes a ticket to one slice of about 10 minutes of agent work where it can (one invariant, one fix with its test), and splits a larger one in the ticket file before spawning. An implementer that finds its ticket larger commits what is green, reports the slice and the next step, and is resumed with `SendMessage`; it does not push on for an hour.
- **Cycles:** a result-style ticket gets a cap (three cycles) and each cycle one bounded run.
- **Late failures** (a peak-day stall at sim 40,000 s): diagnose from a snapshot taken just before it, not by re-running from zero. Run once with `--until time:<a little before it> --snapshot s.json`, then iterate on the stuck state with `--from-snapshot s.json` in seconds. A snapshot is valid only for the engine version that wrote it, so the final proof of a fix is still a full run, not a resumed one.

## Gotchas no check enforces

- Run anything longer than about a minute with `scripts/bg.sh run <log> <command...>` (detached; the log ends with `EXIT <code>`; add `--heavy` for peak-day runs and the smoke suite: one heavy job runs at a time across all worktrees, a second logs a `waiting for heavy lock` line and starts when the first ends; light jobs never wait), then `scripts/bg.sh wait <log> [seconds]` to block until it finishes. Never write your own `sleep` loop: one left running blocks `scripts/remove-worktree.sh`. `scripts/test-bg.sh` tests it.
- The smoke suite is serial; `SMOKE_WORKERS=2` runs two spec files at once (idle machine only; re-run any failure alone before believing it).
- Each `pnpm run test:smoke` picks free ports itself (`playwright.config.ts`), so parallel agents never share one; leave `SMOKE_DEV_PORT` and `SMOKE_PROD_PORT` unset. Stop only processes you started, with `kill <pid>`; never `pkill -f` or `fuser -k`.
- Disk is shared: a worktree with `node_modules` is about 1.2 GB. Implementers delete their worktree's `node_modules`, `.smoke-dist` and `.smoke-results` before reporting; the orchestrator removes the worktree after the merge. Remove worktrees with `git worktree remove` (never a blanket `rm -rf`, which the permission classifier blocks).
- Vitest's timeout is 60 s (`vitest.config.ts`), so `pnpm run verify` runs green on a busy machine; a timeout failure there is a real hang once it reproduces alone (`invariants-incremental.test.ts` has timed out under three parallel agents and passed alone).
- Regenerate goldens only on purpose (`UPDATE_GOLDEN=1 pnpm test`) and say why in the commit. A golden holds an event-log hash, so two tickets that both regenerate the same golden always conflict: resolve by regenerating on the merged tree (`merge-ticket.sh` says how), never by hand. When planning tickets, give a change that moves every golden (a default flip) a ticket of its own, blocked by the tickets whose behaviour it turns on, instead of running such tickets in parallel.
- Never commit `.blend` files (`scripts/check-tracked-files.mjs`, part of `verify`, fails if you do). Reference photos under `docs/reference/` are committed on purpose.
- A full-day peak run at scale 0.25 or more exceeds the 30 minute background limit: stop it at a condition that proves the point (`--until vessels:4`, `--until time:<s>`, `--until moves:<n>`) and say which condition you used.
- **Result-style acceptance** ("the peak day finishes") is open-ended: phase 2 spent four fix cycles and about six hours on one. Brief such a ticket with a cycle cap (three), a bounded run per cycle, and "report the root cause found so far" as a valid result.
- Presets such as `"TTI Algeciras, peak day"` take over two minutes to run to `--until time:7200`: run them in the background with `--events` to a file, then count types with `cut -d, -f… | sort | uniq -c` rather than reading the events.
