# Agent tooling and browser smoke tests

Reference for `AGENTS.md`: reach for it when you run the smoke suite, work in a cloud session, take screenshots, record media, brief an implementer in a worktree, or benchmark Terminal Twin frame rate.

## Browser smoke tests

- **Browser smoke tests** (`pnpm run test:smoke`, Playwright, `src/**/*.smoke.ts`) are not part of `verify`. Run them alone with `scripts/bg.sh run --heavy pnpm run test:smoke <files> --trace off` (a second heavy job or a file edit during the run makes failures); every run ends with one `SMOKE: <n> passed, <n> failed, ...` line (`scripts/smoke-summary-reporter.mjs`), which is the result to report: a pipe (`| tail`) hides the exit code. CI runs them on every PR push that changes `src/` (core plus the selected groups), on every push to `main` and from the Actions tab ("Run workflow"), the last two with every group; the plain `smoke` label runs every group on a PR, and a `smoke:<group>` label adds one. `scripts/smoke-ci.mjs` holds the CI logic (`plan`: groups, grep pattern and the PR comment; `comment`: one PR comment updated in place; `red-main`: the issue a red `main` run opens, `--dry-run` prints it; `node --test scripts/test-smoke-ci.mjs`). `Browser smoke tests (Terminal Twin)` is the required check: it passes as a no-op when no file under `src/` changed. Specs titled `@load` need a real frame rate and never run in CI. Frame assertions are ratios over a minimum wall-clock window (`tests/browser/frameSampling.ts`), never absolute counts. The `dev` project needs the dev API (`window.__tt`, `?viewer=`) and runs against one of two servers (`scripts/smoke-server.mjs`, `node --test scripts/test-smoke-server.mjs`): by default, locally and in CI, the smoke build, a bundled `vite build --mode smoke` into `.smoke-build/` (`SMOKE_BUILD_DIR`) that keeps the dev API, served by `vite preview` (page open to `__tt` ready is faster; a run builds it once at start, about a minute; `pnpm run build:smoke` builds it and `SMOKE_BUILD_PREBUILT=1` serves it without rebuilding, as CI shards do, so set it when re-running specs against an unchanged app). Local runs and CI serve the same bundle, so asset URLs carry the same hashed names (`hero-shc-<hash>.glb`): a spec matches an asset by prefix or extension (`/hero-shc[.-]/`), never by a plain `name.ext` (#344). `SMOKE_SERVER=dev` opts in to the Vite dev server (no build step, hot reload, unhashed names) for debugging a spec while editing the app; a pass there does not prove a pass in CI. Code gated on the dev API checks `import.meta.env.DEV || import.meta.env.MODE === 'smoke'`, which folds to false in a production build; specs that read `process.env.SMOKE_SERVER` (set by the config) can tell the two servers apart (`build-stamp.smoke.ts`). The `prod` project (`*.prod.smoke.ts`) uses a production build. Each run picks free ports unless `SMOKE_DEV_PORT` / `SMOKE_PROD_PORT` pin them. In CI (`CI` set) a failing test is retried once (a pass on retry is reported as flaky) and the run stops after 5 failures; local runs have no retries and no cap. Setting `SMOKE_JSONL_REPORT=<file>` appends one JSON line per finished test attempt (`scripts/smoke-jsonl-reporter.mjs`, `node --test scripts/test-smoke-jsonl-reporter.mjs`), so a cancelled or timed-out run keeps its timings (CI sets it, one file per shard, and merges them); `SMOKE_JSON_REPORT=<file>` writes a Playwright JSON report, only when the run ends. `node scripts/smoke-timing.mjs <file>...` turns either (several files, one per shard, read together) into a duration-sorted Markdown table with a scene column, and flags every test over the 30 s budget (`--budget <s>`) in its row and in a `[!WARNING]` block, a warning that never fails the run (`node --test scripts/test-smoke-timing.mjs`).
- **Smoke spec review rule (judgement, not a lint):** a spec reads anything the render loop applies on a later frame (lighting mode, LOD, hero models, close-ups, colour) with `expect.poll` or `waitForFunction`, so a slow CI frame still passes. A single read straight after a step is a finding for `/code-review`. Phase 1 example: the night-mode check in `terminal-twin-atmosphere.smoke.ts` read the lighting once after `__tt.step()`, passed locally and failed twice in CI, while its sibling test in the same file polled (fixed in commit dcd7738).
- **Smoke groups:** every test of a smoke spec file carries one group tag (`test('title', { tag: '@camera' }, ...)`; groups in `scripts/smoke-groups.mjs`: `core` (boot, production-build, URL switches, render budget, home page, build stamp, menu volume; always runs), `shell`, `camera`, `setup`, `analysis`, `vessel`, `equipment`, `yard`, `engine`); `@load` and `@baseline` are extra tags, not groups. `node scripts/check-smoke-groups.mjs` (in `verify` and CI) fails on a spec with no group tag or more than one. `node scripts/smoke-select.mjs [--labels a,b] [--base B --head H | --files-from F] [--grep]` prints the groups a change needs and why: nothing when no file under `src/` changed, else `core`, every `smoke:<group>` label, every group `scripts/smoke-map.txt` maps a changed path to (Markdown, `docs/`, `cli/` and `*.test.ts` never add one) and the group of each changed spec; the plain `smoke` label selects all. `--grep` prints a Playwright pattern (`@core|@camera`) for `pnpm run test:smoke --grep`. Tests: `node --test scripts/test-check-smoke-groups.mjs scripts/test-smoke-select.mjs`. A new spec takes a group tag; a new area gets a map line.
- **Sharded CI smoke run** (`.github/workflows/pr-checks.yml`): `Smoke build` (job `smoke-build`) builds `.smoke-build/` (`pnpm run build:smoke`) and `.smoke-dist/` (production) once, counts the tests (`playwright test --list --grep-invert @load`) and uploads both bundles as the `smoke-bundles` artifact. It also balances the shards by test time: `node scripts/smoke-shards.mjs --list <playwright --list output> --shards 6 --out .smoke-shards [history.jsonl...]` (`node --test scripts/test-smoke-shards.mjs`) writes one `--test-list` file per shard, longest test first, each to the shard with the least time so far. Times come from the per-test JSONL of the last green run (the step `gh run download`s the merged `smoke-report` artifact of the newest of the last 20 successful `pr-checks.yml` runs that has one; job permission `actions: read`), then from the committed fallback `scripts/smoke-timings.jsonl` (same JSONL format; estimated from PR #341's shard totals and #345's viewer times, so refresh it from a CI run's `smoke-report` artifact when the suite changes a lot: `cat smoke-report/*/results.jsonl > scripts/smoke-timings.jsonl`), and a test in neither counts as the average; the step prints each shard's predicted time. The shard files travel in the `smoke-bundles` artifact. Six `Browser smoke tests (shard i/6)` jobs (`smoke-shard`, `fail-fast: false`) download it and run `pnpm run test:smoke --grep-invert @load --test-list .smoke-shards/shard-i.txt` with `SMOKE_BUILD_PREBUILT=1` and `SMOKE_PROD_PREBUILT=1` (`SMOKE_PROD_DIR`, default `.smoke-dist`; `scripts/smoke-server.mjs`), so no shard builds; each uploads its JSONL as `smoke-report-shard-i`. `playwright.config.ts` sets `fullyParallel: true`, so a shard is a set of tests, not files (by file, three shards once took 7, 9 and 19 min; by count in file order, PR #341's six took 7.2 to 1.5 min, which is why they are balanced by time); specs must not share state between tests (no serial describe, no page kept across tests), and local runs stay on one worker. The `Browser smoke tests (Terminal Twin)` job (`smoke`) runs `node scripts/smoke-merge.mjs <shard.jsonl>... --expect <count> --summary "$GITHUB_STEP_SUMMARY"`: one `SMOKE:` line, one timing table with the 30 s flags, and exit 1 when a test failed, fewer tests were reported than counted (a shard cancelled or timed out), or a test ran in two shards (`node --test scripts/test-smoke-merge.mjs`); it also fails when a shard job failed outside its tests. Check shard balance locally: `pnpm exec playwright test --list --grep-invert @load > list.txt && node scripts/smoke-shards.mjs --list list.txt --shards 6` prints the predicted time per shard; `--shards 4` showed 3.5 min a shard against 2.4 min for 6 on the fallback, more than the minute of setup a shard costs, so CI keeps 6.
- **Dispatch from the CLI:** `gh workflow run pr-checks.yml --ref <branch>` starts the sharded smoke run in CI (the Actions tab "Run workflow" does the same); `gh run watch` follows it. Use it to see whether a failure is specific to this machine before bisecting.

## Tooling

- **Cloud sessions:** a SessionStart hook (`.claude/hooks/session-start.sh`) runs `pnpm install` and sets `core.hooksPath` to `.githooks` (its `commit-msg` rejects a `Co-Authored-By` trailer); it does nothing locally.
- **Blender in cloud sessions:** opt-in `scripts/install-bpy.sh` (once; idempotent) installs the pinned `bpy` into `$HOME/.cache/tt-bpy-venv` and prints its python path for `pnpm run tt:assets --python <path>`; the session-start hook does not. Details: Terminal Twin `docs/assets-pipeline.md`.
- **Visual checks:** `pnpm run screenshot --path /sim/<sim-id> --wait 8000` saves a PNG to `.screenshots/` and reports page errors (headless Chromium, software WebGL, so no real frame rates). Options: header of `scripts/screenshot.mjs` (`--wait-for-fn`, `--scale`). Terminal Twin close-up: place the camera with `__tt.setCameraPose(...)` in `--eval` and add `--wait-for-fn "__tt.heroSettled() && __tt.perf().stats.heroFaces > 0"` (hero detail takes about a minute here).
- **README media:** `pnpm run capture-readme-media` (after `pnpm run build && pnpm run preview`).
- **Implementer worktrees:** the brief's first step is `scripts/worktree-base.sh <integration-branch>`, which puts the worktree on the integration tip or refuses with a one-line reason (`scripts/test-worktree-base.sh` tests it). Workflow: `docs/agents/implementing.md`. `scripts/merge-ticket.sh` sets the ticket's `handover.md` row after a green merge (`scripts/test-merge-ticket.sh`); `scripts/bg.sh` runs a long command detached and waits on its `EXIT` line (`run --heavy` takes the one machine-wide heavy lock, so peak-day runs and the smoke suite queue instead of overlapping); when a job ends, fails or is stopped, `bg.sh` ends every process it started (each inherits a `BG_JOB` marker in its environment, so Playwright web servers in their own session and orphaned children are found too: TERM, then KILL after 5 s), and `scripts/bg.sh stop <log>` stops a running job that way (its log ends `EXIT 143`); processes the job did not start are never touched (`scripts/test-bg.sh`); `scripts/proof-runner.sh` runs several `tt:run` variants in parallel under the heavy lock and prints one table (`scripts/test-proof-runner.sh`); `scripts/timebox.sh` sets and reads an agent's wall-clock budget (`scripts/test-timebox.sh`); `scripts/remove-worktree.sh` removes a finished agent's worktree, locked or not, and refuses one in use (`scripts/test-remove-worktree.sh`).
- **Frame-rate benchmark:** `scripts/bench-preflight.sh` (quiet-machine check), `pnpm run build` then the `preview` entry of `.claude/launch.json` (port 4173), then the Benchmark button; `pnpm run tt:frame-report <file.json> [--record]` reads the JSON. Procedure: Terminal Twin `docs/optimising/frame-rate.md`.
- **Windows (Git Bash):** without `flock`, `scripts/bg.sh run --heavy` takes an mkdir lock directory (`bg-heavy.d` in the git common dir, holding the owner pid, a dead owner counts as free), so heavy jobs still queue and `scripts/bench-preflight.sh` still answers.
- **Laptop-only work** (needs a real GPU or the owner's eye): `gh issue list --label needs-gpu`. Cloud sessions and CI have software WebGL only.
