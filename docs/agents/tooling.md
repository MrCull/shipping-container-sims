# Agent tooling and browser smoke tests

Reference for `AGENTS.md`: reach for it when you run the smoke suite, label a PR with its smoke groups, work in a cloud session, take screenshots, record media, brief an implementer in a worktree, or benchmark Terminal Twin frame rate.

## Unit-test scope

- **`pnpm run verify [base]`**: `verify:checks` (dependency, tracked-file, em dash and other checks, the `node --test` script tests, lint, build; whole app) then `node scripts/unit-select.mjs --run [base]`, which prints `unit-select: base <sha> (<how>)`, `unit-select: scope all|none|<sim ids>`, one `<path>: <reason>` line per changed path, any `skip sim <id>` line (a sim with no unit tests has no vitest project) and the projects it runs, then runs `vitest run --project <id>...` (every project for `all`; nothing and exit 0 for `none`). An unresolvable base exits 2. Selection rule and base: AGENTS.md **Verification**. `--files-from FILE` reads the changed paths from a file; `--json` prints `{ base, how, scope, projects, skipped, reasons }` (`projects` is `"all"` or a list) for CI.
- **`pnpm run verify:all`**: the same checks, then every unit test (`pnpm test`).
- **`pnpm test:sim <id>`**: one sim's vitest project, with its total wall time (`scripts/test-sim.mjs`).

## Browser smoke tests

- **Browser smoke tests** (`pnpm run test:smoke`, Playwright, `src/**/*.smoke.ts`) are not part of `verify`.
  - Run them alone with `scripts/bg.sh run --heavy pnpm run test:smoke <files> --trace off` (a second heavy job or a file edit during the run makes failures); every run ends with one `SMOKE: <n> passed, <n> failed, ...` line (`scripts/smoke-summary-reporter.mjs`), which is the result to report: a pipe (`| tail`) hides the exit code.
  - When CI runs which groups, and the labels: **Smoke labels** below.
  - `scripts/smoke-ci.mjs` holds the CI logic (`plan`: groups, grep pattern and the PR comment; `comment`: one PR comment updated in place; `red-main`: the issue a red `main` run opens, `--dry-run` prints it; `node --test scripts/test-smoke-ci.mjs`).
  - Specs titled `@load` need a real frame rate and never run in CI; local runs leave them out too unless `SMOKE_LOAD=1` (`playwright.config.ts` `grepInvert`). Frame assertions are ratios over a minimum wall-clock window (`tests/browser/frameSampling.ts`), never absolute counts.
  - The `dev` project needs the dev API (`window.__tt`, `?viewer=`) and runs against one of two servers (`scripts/smoke-server.mjs`, `node --test scripts/test-smoke-server.mjs`): by default, locally and in CI, the smoke build, a bundled `vite build --mode smoke` into `.smoke-build/` (`SMOKE_BUILD_DIR`) that keeps the dev API, served by `vite preview` (page open to `__tt` ready is faster; a run builds it once at start, about a minute; `pnpm run build:smoke` builds it and `SMOKE_BUILD_PREBUILT=1` serves it without rebuilding, as CI shards do, so set it when re-running specs against an unchanged app).
  - Local runs and CI serve the same bundle, so asset URLs carry the same hashed names (`hero-shc-<hash>.glb`): a spec matches an asset by prefix or extension (`/hero-shc[.-]/`), never by a plain `name.ext` (#344).
  - `SMOKE_SERVER=dev` opts in to the Vite dev server (no build step, hot reload, unhashed names) for debugging a spec while editing the app; a pass there does not prove a pass in CI.
  - Code gated on the dev API checks `import.meta.env.DEV || import.meta.env.MODE === 'smoke'`, which folds to false in a production build; specs that read `process.env.SMOKE_SERVER` (set by the config) can tell the two servers apart (`build-stamp.smoke.ts`).
  - The `prod` project (`*.prod.smoke.ts`) uses a production build. Each run picks free ports unless `SMOKE_DEV_PORT` / `SMOKE_PROD_PORT` pin them.
  - In CI (`CI` set) a failing test is retried once (a pass on retry is reported as flaky) and the run stops after 5 failures; local runs have no retries and no cap.
  - Setting `SMOKE_JSONL_REPORT=<file>` appends one JSON line per finished test attempt (`scripts/smoke-jsonl-reporter.mjs`, `node --test scripts/test-smoke-jsonl-reporter.mjs`), so a cancelled or timed-out run keeps its timings (CI sets it, one file per shard, and merges them); `SMOKE_JSON_REPORT=<file>` writes a Playwright JSON report, only when the run ends.
  - `node scripts/smoke-timing.mjs <file>...` turns either (several files, one per shard, read together) into a duration-sorted Markdown table with a scene column, and flags every test over the 30 s budget (`--budget <s>`) in its row and in a `[!WARNING]` block, a warning that never fails the run (`node --test scripts/test-smoke-timing.mjs`).
- **Smoke spec review rules** (judgement, not lints; `/code-review` and the implementer brief apply them to every new or changed smoke spec):
  - **One group tag** on every test, the group of the area it checks (**Smoke labels** below).
  - **Smallest fixture** that proves the behaviour (the sim guide's "Test levels"); a TTI preset only for scale.
  - **Lowest level** that can see the behaviour: engine state in a unit test, scene state in the headless scene, a panel in a component test; the smoke spec keeps the wiring.
  - **30 s budget** per test, or a comment at the test saying why it needs more.
  - **Draw counts:** a spec that reads draw calls or triangles (`__tt.renderOnce()`, `scene().render`) opens with `openTwin`'s `assets` naming every GLB set its view draws. A set still loading draws a placeholder with another count, and `--repeat-each` cannot show it: only a worker's first test pays the load (#305's boom test drew 52 calls against 48 in CI).
  - **Shared-page leaks:** a test on the shared page (`tests/browser/twinTest.ts`) waits for its own scenario's ids and state, never for state that only an earlier test or a fresh page would leave (an asset already requested, a grid already built). Run a changed spec with `--repeat-each=2`: the second run of each test lands on the page the first one left. Phase 2's dashboard chunk, vessel-hulls and hero-equipment flakes (fixed in #338 and #340) were of this kind.
  - **Frame-loop reads:** a spec reads anything the render loop applies on a later frame (lighting mode, LOD, hero models, close-ups, colour), or anything still easing (a camera move, a sound gain following the camera), with `expect.poll` or `waitForFunction`, so a slow CI frame still passes. A single read straight after a step is a finding for `/code-review`. Phase 1 example: the night-mode check in `terminal-twin-atmosphere.smoke.ts` read the lighting once after `__tt.step()`, passed locally and failed twice in CI, while its sibling test in the same file polled (fixed in commit dcd7738). Phase 2: `gantry-alarm.smoke.ts` stored the alarm gain in a variable mid camera ease and failed CI (0.138 against more than 0.2; fixed in commit 81e9bae). A read stored in a variable first is the same finding, which is why no lint rule catches it.
- **Smoke groups:** every test of a smoke spec file carries one group tag (`test('title', { tag: '@camera' }, ...)`; groups in `scripts/smoke-groups.mjs`: `core` (boot, production-build, URL switches, render budget, home page, build stamp, menu volume, headless parity, shared-page reset; runs for every `src/` change except a sim-only one), `shell`, `camera`, `setup`, `analysis`, `vessel`, `equipment`, `yard`, `engine`); `@load` and `@baseline` are extra tags, not groups. `node scripts/check-smoke-groups.mjs` (in `verify` and CI) fails on a spec with no group tag or more than one. `node scripts/smoke-select.mjs [--labels a,b] [--base B --head H | --files-from F] [--grep]` prints the groups a change needs and why: nothing when no file under `src/` changed and no `smoke` or `smoke:<group>` label is set, else `core`, every `smoke:<group>` label, every group `scripts/smoke-map.txt` maps a changed path to (Markdown, `docs/`, `cli/` and `*.test.ts` never add one) and the group of each changed spec; the plain `smoke` label selects all. `--grep` prints a Playwright pattern (`@core|@camera`) for `pnpm run test:smoke --grep`. Tests: `node --test scripts/test-check-smoke-groups.mjs scripts/test-smoke-select.mjs`. A new spec takes a group tag; a new area gets a map line.
  - A **sim-only change** (every changed `src/` path under `src/sims/<id>/`, no plain `smoke` label) runs the home wall spec (`@home-wall`, an extra tag on `src/tests/browser/home-wall.smoke.ts`) in place of `core`; a `smoke:core` label or a map line naming `core` brings `core` back, and any `src/` change outside `src/sims/` keeps it. Map lines under a `[src/sims/terminal-twin/]` scope line match only inside that folder, so another sim's `bay*`, `truck*` or `ui/` file selects no Terminal Twin group; the few unscoped lines (after `[]`) are shared `src/` paths, each with a comment saying why.
- **Sharded CI smoke run** (`.github/workflows/pr-checks.yml`): `Smoke build` (job `smoke-build`) builds `.smoke-build/` (`pnpm run build:smoke`) and `.smoke-dist/` (production) once, lists the selected tests (`playwright test --list --grep-invert @load`, plus the selection's `--grep`) and uploads both bundles as the `smoke-bundles` artifact.
  - It also balances the shards by test time: `node scripts/smoke-shards.mjs --list <playwright --list output> --shards auto --max-shards 6 --out .smoke-shards [history.jsonl...]` (`node --test scripts/test-smoke-shards.mjs`) picks the shard count (one per 2.5 min of predicted time, 1 to 6) and writes one `--test-list` file per shard, longest test first, each to the shard with the least time so far.
  - Times come from the per-test JSONL of the last green run (the step `gh run download`s the merged `smoke-report` artifact of the newest of the last 20 successful `pr-checks.yml` runs that has one; job permission `actions: read`), then from the committed fallback `scripts/smoke-timings.jsonl` (same JSONL format; estimated from PR #341's shard totals and #345's viewer times, so refresh it from a CI run's `smoke-report` artifact when the suite changes a lot: `cat smoke-report/*/results.jsonl > scripts/smoke-timings.jsonl`), and a test in neither counts as the average; the step prints each shard's predicted time.
  - The shard files travel in the `smoke-bundles` artifact. One `Browser smoke tests (shard i/n)` job per shard (`smoke-shard`, `fail-fast: false`) download it and run `pnpm run test:smoke --grep-invert @load --test-list .smoke-shards/shard-i.txt` with `SMOKE_BUILD_PREBUILT=1` and `SMOKE_PROD_PREBUILT=1` (`SMOKE_PROD_DIR`, default `.smoke-dist`; `scripts/smoke-server.mjs`), so no shard builds; each uploads its JSONL as `smoke-report-shard-i`.
  - `playwright.config.ts` sets `fullyParallel: true`, so a shard is a set of tests, not files (by file, three shards once took 7, 9 and 19 min; by count in file order, PR #341's six took 7.2 to 1.5 min, which is why they are balanced by time); specs must not share state between tests (no serial describe, no page kept by a spec across tests; the one exception is the Terminal Twin fixture `tests/browser/twinTest.ts`, #329, which keeps one page per worker and resets it before every test, so a shard that runs any subset in any order is fine; `--shuffle <seed>` checks order independence locally), and local runs stay on one worker.
  - The `Browser smoke tests (Terminal Twin)` job (`smoke`) runs `node scripts/smoke-merge.mjs <shard.jsonl>... --expect <count> --summary "$GITHUB_STEP_SUMMARY"`: the failed and flaky tests by name, then one `SMOKE:` line as the last line it prints (only the checkout cleanup follows it, about 17 lines, so a 25-line tail of the job log holds the result), one timing table with the 30 s flags, and exit 1 when a test failed, fewer tests were reported than counted (a shard cancelled or timed out), or a test ran in two shards (`node --test scripts/test-smoke-merge.mjs`); it also fails when a shard job failed outside its tests.
  - Check shard balance locally: `pnpm exec playwright test --list --grep-invert @load > list.txt && node scripts/smoke-shards.mjs --list list.txt --shards auto` prints the shard count and the predicted time per shard (`--shards 4` fixes the count).
- **Dispatch from the CLI:** `gh workflow run pr-checks.yml --ref <branch>` starts the sharded smoke run in CI (the Actions tab "Run workflow" does the same); `gh run watch` follows it. Use it to see whether a failure is specific to this machine before bisecting.

## Smoke labels

Every PR that changes `src/` carries the `smoke:<group>` label of each area it touches. CI runs `core` (for a sim-only change, every changed `src/` path under `src/sims/<id>/`, only the home wall spec in its place, and the PR comment says so) plus the groups from those labels, from the changed paths (`scripts/smoke-map.txt`) and from changed specs, and keeps one PR comment saying why each group ran. The plain `smoke` label, a manual Run workflow and every push to `main` run every group; a red run on `main` opens a `needs-triage` issue. A PR with no `src/` change and no `smoke` or `smoke:<group>` label runs none, and the required check `Browser smoke tests (Terminal Twin)` passes as a no-op.

| Label | Area of the system |
| --- | --- |
| `smoke:core` | boot, URL switches, render budget, production build, home page, build stamp, menu music, headless parity, shared-page reset (runs for every `src/` change; a sim-only change runs only the home wall spec) |
| `smoke:shell` | HUD, top bar, views, pacing, display settings, volume and FPS chip, phone layout |
| `smoke:camera` | camera, keyboard and wheel zoom, follow |
| `smoke:setup` | setup dialog, scenario picker, presets, equipment and subsystem modes, yard start, saves |
| `smoke:analysis` | KPIs, dashboard, debugger and inspector, vessel status |
| `smoke:vessel` | hulls, bays and bay viewer, ROB, hatch covers, crane plan, colour by |
| `smoke:equipment` | STS, ASC, SHC, trucks, spreaders, hero models, gantry alarm |
| `smoke:yard` | containers and close-ups, infrastructure, atmosphere, hero faces, scene performance |
| `smoke:engine` | the worker running a fixture to its golden hash (engine checks live in unit and headless tests) |

Each smoke test carries exactly one group tag (`{ tag: '@camera' }`, checked in `verify`) and stays under 30 s; CI's timing table flags any test over the budget, and a test that needs more says why in a comment. Review rules for smoke specs: **Browser smoke tests** above.

Local runs use the smoke build (the bundled app with the dev API `window.__tt`) at Low quality with rendering off (`openTwin`'s defaults), one worker, one shared page per worker reset between tests (#329, `tests/browser/twinTest.ts`). Run one group alone with `scripts/bg.sh run --heavy <log> pnpm run test:smoke --project=dev --grep-invert @load --grep @<group>` and report the `SMOKE:` line.

## Tooling

- **Reading another branch:** `git show <ref>:<path>` prints to stdout; read it there or pipe it, and write any copy only inside your scratchpad.
- **Nightly peak day** (`.github/workflows/peak-day.yml`, also Run workflow): runs "TTI Algeciras, peak day" to `--until vessels:5` and judges its `--out` summary with `scripts/peak-day-check.mjs` (`node --test scripts/test-peak-day-check.mjs`). Fewer than 5 vessels, a violation or a first error fails it and opens one `needs-triage` issue, or comments on the open one; the run log and summary are the `peak-day-run` artifact. It guards the stall no PR check sees: a run that goes idle with 0 violations (#365).
- **Doc engine version** (`scripts/check-doc-engine-version.mjs`, in `verify` and CI): a Terminal Twin doc changed on the branch must say `Checked against ENGINE_VERSION <current>` when it has that line; `reports/` are skipped. Base: `DOC_VERSION_BASE` (CI: `HEAD^1`), else the merge-base with `origin/main`.
- **Cloud sessions:** a SessionStart hook (`.claude/hooks/session-start.sh`) runs `pnpm install` and sets `core.hooksPath` to `.githooks` (its `commit-msg` rejects a `Co-Authored-By` trailer); it does nothing locally.
- **Blender in cloud sessions:** opt-in `scripts/install-bpy.sh` (once; idempotent) installs the pinned `bpy` into `$HOME/.cache/tt-bpy-venv` and prints its python path for `pnpm run tt:assets --python <path>`; the session-start hook does not. Details: Terminal Twin `docs/assets-pipeline.md`.
- **Visual checks:** `pnpm run screenshot --path /sim/<sim-id> --wait 8000` saves a PNG to `.screenshots/` and reports page errors (headless Chromium, software WebGL, so no real frame rates). Options: header of `scripts/screenshot.mjs` (`--wait-for-fn`, `--scale`). Terminal Twin close-up: place the camera with `__tt.setCameraPose(...)` in `--eval` and add `--wait-for-fn "__tt.heroSettled() && __tt.perf().stats.heroFaces > 0"` (hero detail takes about a minute here).
- **README media:** `pnpm run capture-readme-media` (after `pnpm run build && pnpm run preview`).
- **Implementer worktrees:** the brief's first step is `scripts/worktree-base.sh <integration-branch>`, which puts the worktree on the integration tip or refuses with a one-line reason (`scripts/test-worktree-base.sh` tests it). Workflow: `docs/agents/implementing.md`. `scripts/merge-ticket.sh` sets the ticket's `handover.md` row after a green merge (`scripts/test-merge-ticket.sh`); `scripts/bg.sh` runs a long command detached and waits on its `EXIT` line (`run --heavy` takes the one machine-wide heavy lock, so peak-day runs and the smoke suite queue instead of overlapping); when a job ends, fails or is stopped, `bg.sh` ends every process it started (each inherits a `BG_JOB` marker in its environment, so Playwright web servers in their own session and orphaned children are found too: TERM, then KILL after 5 s), and `scripts/bg.sh stop <log>` stops a running job that way (its log ends `EXIT 143`); processes the job did not start are never touched (`scripts/test-bg.sh`); `scripts/proof-runner.sh` runs several `tt:run` variants in parallel under the heavy lock and prints one table (`scripts/test-proof-runner.sh`); `scripts/timebox.sh` sets and reads an agent's wall-clock budget (`scripts/test-timebox.sh`); `scripts/remove-worktree.sh` removes a finished agent's worktree, locked or not, and refuses one in use (`scripts/test-remove-worktree.sh`).
- **Experiments and the heavy lock:** `pnpm run tt:experiment` takes the same heavy lock as `scripts/bg.sh run --heavy` from Node (`src/sims/terminal-twin/cli/heavyLock.ts`, holder `tt:experiment <out>`, skipped under `BG_HEAVY_HELD=1`; `tests/experiment-heavy-lock.test.ts`) and runs replicates in `--jobs` worker processes.
- **Frame-rate benchmark:** `scripts/bench-preflight.sh` (quiet-machine check), `pnpm run build` then the `preview` entry of `.claude/launch.json` (port 4173), then the Benchmark button; `pnpm run tt:frame-report <file.json> [--record]` reads the JSON. Procedure: Terminal Twin `docs/optimising/frame-rate.md`.
- **Windows (Git Bash):** without `flock`, `scripts/bg.sh run --heavy` takes an mkdir lock directory (`bg-heavy.d` in the git common dir, holding the owner pid, a dead owner counts as free), so heavy jobs still queue and `scripts/bench-preflight.sh` still answers.
- **Laptop-only work** (needs a real GPU or the owner's eye): `gh issue list --label needs-gpu`. Cloud sessions and CI have software WebGL only.
